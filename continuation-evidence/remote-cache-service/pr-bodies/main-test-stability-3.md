## Summary

One test-only fix for a failure seen twice on main heads and once on an unrelated PR. It makes five tests wait for the release they were already implicitly depending on, instead of reading ownership counts while a worker may still hold the receiver. No production code changes and no assertion is relaxed. The fix does not reproduce the failed CI runs themselves; the section says so.

## Ownership reads after a sharing pass or lazy attempt: wait for the attempt's release

A sharing pass waits for its `RunLazyTask` callers, which can return before the attempt workers drop their own receiver holds, so a hold count read right after the pass could see three holds where the test's original two were expected; the same boundary exists after a demanded acquisition returns. That is an observation before a deferred release, not leaked ownership. The five tests that read ownership after such a boundary now arm the existing bounded attempt-release hook before triggering the work and wait on it before their post-pass or post-acquisition checks: `TestSnapshotSharingReleaseThenExternalFinish`, `TestSnapshotSharingAbortReportsAfterCleanup`, `TestSnapshotSharingCancelAfterPublicationDeliversReceipt` and `TestSnapshotSharingFailedFinishLastOwner` in `dagql/cache_snapshot_sharing_test.go`, and `TestOfferSettlementReplacement` (all four subcases) in `dagql/cache_offer_matrix_test.go`; its failed-sync subcases wait a second time for the bookkeeping retry that `joinPartInstallation` starts as another lazy task. Assertions made while a receipt, preparation or acquisition is deliberately blocked are preserved, and the existing attempt-release and session-completion barriers stay in place.

Evidence: the four sharing tests passed 200 of 200 repetitions under `-race` with a 120-second timeout before and after the change (no local reproduction in the baseline); `TestOfferSettlementReplacement` passed 50 parents and 200 subcases under the same command before and after, the "after" run including both the initial-attempt and bookkeeping-retry waits; the full `dagql` package passed once with a 60-second timeout (527 top-level PASS, one inherited nested SKIP), all on the saved pre-commit patch byte-identical to this change. The recorded failures (main 34ad873d78's test-base, trace `2d04e43aac9231230ffc91bce24ef41c`, `cache_snapshot_sharing_test.go:1228`, expected 2 actual 3; and the same boundary in the twelfth item's `TestSnapshotSharingCancelDuringPreparation`, main 50164dc9db's test-base trace `7913f1583003bef7970ee6fe46d4f136` and #14273's trace `cb0082f1aa097829451b13a08e4ce8b9`, line 1127, fixed on main by #14278) did not reproduce locally, so the diagnosis follows the source contract rather than a replay of those runs.
