**The intended result and its boundaries.** Another engine must be able to receive selected cached values and their dependencies, use ordinary cache lookup, and obtain filesystem content when it is needed. The remote service chooses what to export or offer; this effort supplies engine operations. It does not implement that service, its transport, or a synchronous remote request on every miss.

For example, engine B should import a Container produced on engine A without immediately downloading its filesystem. On filesystem demand, it can use an available local snapshot, try a supplied snapshot chain, or run the original lazy producer when remote content is unavailable. Both completed and pending values need their original producer inputs. Metadata-only use must remain metadata-only, and imported state must survive save/reopen without forcing bytes or ancestor evaluation.

The accepted direction extends existing lazy evaluation, persistence, and snapshot transfer. Preserve ordinary cache equivalence and resource/session ownership. Translate declared engine-local references in typed representations; do not reinterpret arbitrary JSON strings or transport engine-local equivalence-class numbers. A value-dependency graph and a filesystem layer chain serve different purposes. Selective Container parts and existing computation groups must remain coherent together.

The Human accepted ordinary nondeterminism: pruning a File does not invalidate every function result that once read it, and different lazy outputs need not all come from one execution. Missing an optimization is acceptable; teaching incorrect equality is not. Export should carry a small, explicit set of safe extra digests, such as pinned image identity, and omit unsafe content-derived extras without smuggling their equality through aliases. Layer digests were not accepted as substitutes for Dagger tree-content hashes.

Keep normal local errors: a missing locally restored snapshot and a persisted decode error retain their existing meaning. Remote download-to-producer fallback is not a general rewrite of local failure semantics. Holds during a real export are appropriate; indefinite retention while awaiting a hypothetical export request is unnecessary. Image metadata without unpacking is in scope, and existing lazy groups already provide relevant structure that must be inspected before proposing new code.

The rejected requirements remain excluded: replacing the existing equality model, conditioning value reuse on byte availability, a general observation/proof/pin system, nested-client forwarding obligations derived from that system, unrelated service identities and hashing changes, broad LLM/runtime work, mutable backing-store transfer, compatibility migrations, a new hostile-input framework, and a fake remote-service project.
