    What-if-cached: design

    wcprof cache-performance analysis · 2026-07-06 · verified against the implementation at commit bb7625e2c and against the engine's caching machinery and op implementations — the dagql cache core, lazy evaluation, key derivation/scoping, and the Container/Directory/File/from/services/module/host resolvers (every mechanism statement here was checked against that code; the map is in the appendix).

    What this tool does, in plain words

    You record one run of a Dagger workload with the wall-clock profiler. You then ask: "how long would this run have taken if these operations had been cache hits?" The tool answers by re-simulating the recorded run with those operations' work removed — the same discrete-event replay that powers the profiler's existing bottleneck rankings. The answer is about the recorded run: its prices, its schedule, its concurrency. The primary customer is the remote-caching effort, which today answers such questions by actually running workloads with and without cache — slow, expensive, and unable to explore many strategies. One recorded run plus many cheap simulations replaces that loop.

    1. The doctrine (binding for every line of this feature)

    1. The model must make sense on its own. For any hypothesis there is a single answer derivable by logic from the recorded data, and that is the answer the tool must produce. Nothing else.
    2. The analyzer takes the data exactly as it is. It never compensates for missing, unresolvable, or inconvenient data — no silent defaults, no guessed values, no assumed demand, no inferred producers, no heuristics under any name. Where data is missing, the fix is on the recording side.
    3. Degradation is bounded, counted, and loud. When the analyzer must act on incomplete data, its behavior stays a pure function of what is recorded, every firing increments a visible counter, and a gate fails (or the report refuses) when firing could change the answer — unless the degradation is provably harmless, with the proof written down.
    4. Every causal claim is verified with its evidence shown, or labeled a hypothesis with its discriminating test named in the same sentence. This applies to design documents, reports, and conversation alike.
    5. Model simplifications are stated, with their error direction, and visible in output — counts and durations, not adjectives. The refinement path for a simplification must be a data path, never an analyzer heuristic.

    Consequence for testing: because answers are derivable by logic, every test scenario states its expected outcome before running — the reasoned catalog in hack/designs/whatif-cached-design.md is the feature's primary QA instrument (§7.1).

    2. The question, precisely — and the non-goals

    In scope: given one profiled run and a set of operations hypothesized as cached, compute the run's counterfactual wall-clock: which recorded work would not have run, and what the schedule — with all its real concurrency, waits, and critical-path shifts — would then have looked like. Rank candidate operations by that saving.

    Out of scope, by the nature of the problem (each is a stated boundary, not a defect):

    Not modeledWhy
    Another run's absolute timea different run has its own prices (network, disk, load) that no simulation of this run can know; comparisons across runs must respect that (§7.4)
    Cache hits for scope-limited keys beyond their scopethe engine deliberately mixes scope values into some cache keys: per-client, per-session (Container.from with a tag — but a digest-pinned ref is exempt and fully cacheable), per-schema, per-call (a fresh random value every invocation — such calls can never hit at all), and arg-driven (noCache-style arguments). These keys cannot hit beyond their scope, by design (§5.3)
    Content reuse below the dagql cachelayer/snapshot sharing in the underlying stores is not addressed by recipe digests; a recipe-digest simulator has no honest claim there
    Lock-contention relieflock waits record the waiter and duration, not the holder; removing a lock-holder therefore never shortens another waiter's recorded delay (error direction: savings understated)
    Resource limitsinherited from the replay's model: unlimited CPU/disk, so freed resources don't speed up surviving work (savings understated on saturated machines)

    3. What the engine records

    The profiler records three event types at the engine's blocking choke points: operations (timed intervals), waits (exact blocked-on intervals), and links (non-blocking facts). Everything below exists identically on both recording paths — the native in-memory recorder and the OTel span pipeline that feeds Dagger Cloud — and one shared graph builder consumes both.

    3.1 Operations and their cache identities

    Op kindWhat it isIts recorded identity (Ident)
    callone dagql cache request, per caller — hits includedthe call's recipe digest (the cache key)
    call_execthe shared execution of a call's resolver; concurrent same-recipe callers wait on one of thesethe same recipe digest
    lazyone run of a result's deferred work (the second phase of a two-phase operation, §3.2), recorded under whichever op first used the resultthe recipe digest of the call whose result it produces
    execa container run by the executorthe recipe digest of the owning withExec call
    service_startservice startup + health checka content digest — recorded for reporting, but service startup is per-session readiness, not result production: a warm run re-starts services even when every result is cached, so this ident never participates in removal (§4.3)
    others (exec_phase, io, session_phase, …)setup phases, leaf I/O, session servingnot call digests; never match a hypothesis

    A call op also records its outcome — hit (cached, payload ready), hit_pending (cached, deferred work not yet run — see §3.2), executed, joined, do_not_cache, ok (the OTel form of a non-hit success), error/canceled — its input digests (the structural inputs of its cache key, recorded at zero extra cost because the cache computes them for its own lookup), and the engine-local result id it returned.

    Three engine facts behind this table, verified in the cache core: implicit inputs — including the scope values of §5.3 — are hashed into the recipe digest itself and are not among the recorded structural input digests, which is why scope is invisible to the analyzer today. Label stability is provable: when the engine later teaches a result a content digest, it forks the call frame — but extra digests are excluded from the recipe hash, so labels derived after teaching still equal the call's recorded digest. In-flight deduplication is per client, so two clients executing the same digest concurrently produce two recorded executions of it — digest-level semantics handles both identically. And errored executions publish no cached result, which grounds the "failures only" eligibility refusal (§5.1).

    3.2 Two-phase operations: where deferred work is recorded

    Most expensive dagql operations run in two phases. The call itself does cheap synchronous work (build the plan; for Container.from, also resolve the registry config). The real work — running the container, materializing a filesystem, pulling layers — runs later, when some operation first uses the result, and is recorded under that consumer, wrapped in a lazy op. 67 deferred-work recipe types implement this across the Container (49), Directory (13), and File (5) families — each with a persisted twin, 133 type declarations in all (count-verified); git, http, host imports, module loading, and services have no such types and do their work inside the call itself. The cache has one entry per call; whether the deferred work has run yet is a separate flag on the cached result — which is why a hit can be hit (work done, payload ready) or hit_pending (recipe cached, first materialization still owed). Two further engine behaviors shape the recorded graphs: a deferred-work recipe usually begins by materializing its parent, so forcing one result can chain into ancestors' deferred work — each run is its own lazy op carrying its own producer's digest, which is exactly why regions nest and the removal rule unions them; and a failed evaluation leaves the result pending and retryable — a retry is a fresh lazy op with the same label, so all attempts join the same digest's regions.

    3.3 Use-markers, and the two suppression counters

    One consumption path would otherwise be invisible: an operation that uses a result whose deferred work already ran takes a fast path that does nothing — and records nothing. So the engine leaves a use-marker there (a zero-duration forced link): "this op needed the result of call digest D, whose production was already complete," pointing at the producing lazy op when this run recorded it. Markers are deduplicated per user, are never timing events, and exist solely so the simulator can see late consumers of nested production (§4.4).

    Two recording-side counters ride in every capture, because these omissions could change answers if they were silent:

    • Ident-derivation failures — a lazy op's producer digest could not be derived, so its label and any use-marker were omitted. Expected zero (the digest is memoized from the cache lookup that admitted the result); the analysis refuses a capture with a nonzero count.
    • Uninstrumented users — a use-marker was not emitted because the using context carried no recorded op (demand from outside the instrumented graph, e.g. an unprofiled session). A declared model boundary, printed as a caveat: savings may be overstated for production such users demanded.

    On the OTel path both facts travel as span links (one per firing, so the tally is exact, and losing one shows up as a dropped link — which the structural gate refuses on any trace carrying wait, marker, or suppression links).

    4. The counterfactual: what "cached" means and what gets removed

    4.1 The hypothesis

    A hypothesis is a set of recipe digests plus a hit cost (default 0). Digest-level — not per-op — because that is what caching means: if digest D's result is in the cache, every caller of D hits, the executor and all its concurrent joiners alike. The hit cost models what a hit itself costs; zero is the local warm hit: the payload is materialized and free to return. (A remote hit that must pull data, and a pending hit that must still materialize on first use, are the same seam with a nonzero cost charged at the right place — future work, §8.1.)

    4.2 The removal rule

    For each hypothesized digest D, resolved statically, before the replay runs:

    1. Every successful non-hit call op with ident D becomes a hit: it finishes at its start + hit cost, replaying none of its recorded self-time, waits, or children. Calls that were already recorded hits are untouched — they were already just lookups.
    2. D's producing work is removed as whole regions: the subtree under each such call, plus the subtree (root included) of every op whose recorded label says "I produce D's result" — the lazy wrappers and container runs of Figure 1, wherever in the graph they were recorded.
    3. A region that anything live still needs is not partially removed — it is kept whole, replays exactly as recorded, and is reported with the reason and its size (§4.4). Partial removal is forbidden because it would require inventing start times for surviving fragments; keeping the whole region keeps the replay's order-independence intact.

    4.3 When removal is refused: the keep rule

    Before anything is removed, every candidate region is tested: does any live operation still need work inside it? "Live" means: not itself removed, and not a hit under this same hypothesis. Three kinds of recorded evidence count as demand, and any one of them keeps the whole region, replayed exactly as recorded, with the reason printed:

    Demand evidenceRule
    A gating wait from a live op targeting an op inside the regionkeeps it — with two reasoned exceptions that are satisfied demand, waived and counted instead: a wait from the region root's own ancestors (the consumer chain that launched the production), and a join on a removed lazy region's root (a concurrent user of that same production — under a warm hit, both get the payload for free)
    A use-marker from a live op naming production inside the region (§3.3)keeps it — unless the marker's digest is itself hypothesized as cached (then its user hits the cache and demands nothing). A marker whose recorded target predates profiling degrades to a containment test over recorded labels — still pure recorded data, only able to add keeps — and any keep it produces is separately counted and marked as degraded evidence in the ranking.
    Structure: the region's root sits inside another region that was keptkeeps it — the kept region replays as recorded, which includes launching this one

    Keeping can revive demand (a kept region's ops are live again), so the test iterates to a fixed point — removal decisions only ever flip toward keeping, so it terminates. Two attribution rules from §3.1 apply throughout: service startup never roots a region and never counts as production evidence (it is per-session readiness a warm run re-pays), and an execution op nested directly under its own same-digest call adds no second region (the call's subtree already covers it).

    4.5 The two invariants the replay enforces

    • Empty hypothesis ⇒ bit-for-bit the baseline simulation. Asserted by test; the counterfactual machinery must add exactly nothing when asked for nothing.
    • Nothing live ever touches removed work. The static resolution guarantees it; the replay still counts any contradiction (ElidedOpDemanded) and fails the result rather than improvising — the same pattern as the replay's other data-faithfulness counters. Zero by construction on faithful data.

    5. Eligibility, selection, and the scope limitation

    5.1 Which digests may be hypothesized

    Checked per digest, refused loudly per reason — never silently filtered:

    StateMeaning / rule
    eligibleat least one successful non-hit call — its calls hit, its production regions become removal candidates
    not foundno call op with this digest in the trace — an error for explicit selections
    do-not-cachethe engine refuses to cache this call; simulating it cached is fiction
    open at capturethe call or its production was still running when the profile was dumped — removal is not determinable
    no recorded outcomesuspect data; never guessed into a hit
    failures onlyfailed results are not cached
    already all hitsa no-op, noted

    FlagResolves to

    5.3 The scope limitation (stated)

    Some cache keys deliberately include a scope value as an implicit input, hashed into the recipe digest itself. The engine's full vocabulary (verified in dagql/cache_inputs.go and the resolvers that opt in):

    Scope inputEffectWho uses it
    per-clienthits only within one clientmodule-source calls; the default of arg-driven caching
    per-sessionhits only within one sessionContainer.from with a tag ref — a digest-pinned ref is exempt and fully cacheable, so pinning restores cross-run cacheability
    per-calla fresh random value every invocation — never hits, everthe noCache-style arm of arg-driven caching
    per-schemahits only under one schema digest (changes across engine/module schema changes)schema-dependent calls

    Because the scope value hides inside the recipe digest (it is not among the recorded structural inputs, §3.1), the simulator cannot currently tell a scoped digest from a portable one — so a cross-run caching strategy built from a ranking may include digests that are unreachable in practice, or (per-call) unreachable anywhere. Within-run questions are unaffected. The remedy is a small recording addition — the engine knows the scope kind at key-derivation time — after which the ranking can mark each digest "cacheable across runs" / "session-scoped" / "never cacheable." Status: planned; recording addition not yet built.

    6. Output: ranking, detail, and refusals

    6.1 The ranking (default on)

    Candidates are formed per call class (all executed digests of the class as one group) plus the top individual executed digests by producing wall-clock; every row is a full re-simulation of that candidate hypothesis — savings are schedule properties, not sums of removed time, and joint savings are not additive across rows (the header says so). A row whose result depended on degraded marker evidence, or whose hypothesis overlaps an unmodeled orphaned demand, is marked DEGRADED-EVIDENCE on the row itself.

    6.2 The explicit-hypothesis detail

    For a selected hypothesis: baseline vs counterfactual makespan; per-digest eligibility with all tallies; every kept region with its reason, size, and demander; the waived-demand and marker counters; and the counterfactual blocking chain — what the new bottleneck would be, walked from the last-finishing root of the simulated schedule.

    6.3 Refusals and gates

    ConditionBehavior
    the capture dropped recorder events, or recorded any ident-derivation suppressionrefuse the what-if-cached sections entirely (demand evidence may be missing / labels incomplete); all violated conditions aggregated into one message
    OTel trace with dropped links while carrying wait/marker/suppression links, missing spans, or failed span-count checksumrefuse (the structural gate)
    anything live demanded removed work during replay (ElidedOpDemanded > 0)the section's result is declared invalid — fail, never patched
    uninstrumented-user suppressions > 0prominent caveat: savings may be overstated for production those users demanded (declared boundary)

    7. How we know it's right

    Four layers, ordered from what the tool fully controls to what it can only be honestly compared against.

    7.1 Reason-first scenario tests

    Because answers are logically derivable (doctrine §1.1), every behavior in §4–§6 is pinned by a synthetic-graph test whose expected value was derived before running: hit short-circuits (executor and joiners), region removal and reflow, every keep-rule row and both waiver shapes, marker demand incl. the hypothesized-digest exception and the degraded containment path, nested hypotheses, eligibility states, selector resolution errors, critical-path shifts (saving < removed time when a second chain takes over), cross-source parity on dual fixtures, and both invariants of §4.5 — including a deliberately corrupted fixture that must trip the violation counter. The catalog lives in hack/designs/whatif-cached-design.md and is the contract: a change is incomplete until its rows are covered.

    7.2 Replay fidelity

    The counterfactual inherits its credibility from the replay: simulating the recorded run unchanged must land on the recorded makespan. Measured on real workloads at ≈0.0% drift; reported on every run as the existing baseline sanity check.

    7.3 Data-faithfulness gates

    All the refusals of §6.3, plus the recording-side suppression counters of §3.3. The design rule they implement: a counter nobody gates on is decoration; every counter here either refuses, fails, or prints a caveat in the sections whose answers it could bend.

    7.4 The empirical check — comparing against a real warm run, honestly

    A cold run and a warm run of the same workload provide real-world evidence — but a warm run is not the counterfactual made flesh, and grading the simulator against its end-to-end time would conflate unrelated quantities. The engine's own semantics guarantee differences that have nothing to do with simulator error: scope-minted keys (§5.3) re-execute warm under new digests at that run's prices; results the cache did not retain across sessions re-execute under the same digests; session setup exists in both runs. And because a makespan is a schedule property, not a sum, a difference of two makespans cannot be honestly attributed to per-item buckets at all. The protocol therefore uses op-partitioned total-recorded-time ledgers over both captures: every recorded op's self-time lands in exactly one named bucket per side, assigned by recorded properties only (kind, outcome, its digest's cross-capture classification, containing region), so the sums are exact by construction. The four makespans (cold actual, cold baseline sim, counterfactual sim, warm actual) print as context lines only; critical chains print as illustration, never as the accounting substrate; no cross-run percentage renders anywhere (test-pinned).     8. Future directions

    8.1 The pull-cost model

    A remote hit costs a pull; a pending hit (recipe cached, work not yet run) costs its first materialization at the first user. The engine's own states point at the right model: the hit cost belongs at the first forcer of the result, not as a constant on every hit call. The current flat per-hit cost (charged at the call) is the stated v1 approximation, exact at cost 0. A real model needs result sizes — not recorded today — and a transfer model; the calibration protocol of §7.4 is the ready-made test bench for it.

    8.2 Scope-aware rankings

    One recorded bit per call (its key includes a session/client scope component) upgrades the §5.3 limitation into an explicit "not cacheable across runs" mark in the ranking.

    8.3 Cache-dependency edges

    Call ops record their cache-key input digests on both sources (§3.1) — the substrate for cache-miss frontier tracing and run comparison (the sibling invalidation-tracing track), unconsumed by this feature so far.
