1. The goal

A run on engine A executes a build graph; its cache results (metadata + content) become available to engine B, which adopts equivalent results as cache hits and materializes their content on demand — downloading snapshot content when available, re-executing the recipe when not. The near-term proof is unchanged: a cold CI run seeds the cache; a warm run on fresh engines shows a real, expected-scale improvement, with counters that demonstrate actual adoption and reuse — and that would have failed loudly if reuse hadn't happened.

The first concrete configuration of that goal is the restart case: one engine persists to disk, a fresh engine boots on that state and gets warm hits. It is the same problem as the remote case with the transport removed, and it is provable entirely in-repo (R11).

Scope of this take (owner-confirmed): engine changes only. The remote service/transport is not part of this batch of work — it stays in the goal statement above as the end state everything must remain compatible with, but nothing here designs or builds it.

2. The structural shift from the previous take

The previous take coupled two layers that must stay separate. The engine's existing identity layer (the e-graph: equivalence classes over calls/results, merged live as work completes) was extended so that content state (filesystem snapshots, metadata, materialization status) was shared across equivalence classes and reconciled continuously — any equivalent result could serve any sibling's content at any moment, including mid-run. Protecting running work from that live movement required a transactional machinery (run-private overlays, reader-audience classification, evaluation gates, instance binding, three interacting locks) whose correctness surface was every reader, writer, and entry point in the engine. That machinery generated its own bug supply and consumed the effort.

This design keeps the identity layer exactly as it is on main, and demotes interchangeability from a continuous runtime invariant to a decision-point policy: equivalence is consulted when it matters — at lookup (pick one winner and materialize that result), at publication, at import — and content state has exactly one home per result, mutated only at well-defined points under ordinary locking. Runs build private values, as they do on main today, and touch the cache only when they publish.

3. Requirements and non-goals

Normative text. Provenance tags: CARRIED from the previous take's requirements (re-adjudicated at reset), REWRITTEN this take, NEW this take. Adjudication history lives in the review log (§4); the previous take's verbatim originals are in ../01-engine-baseline-design.md §1.

R1 — Dual materialization paths CARRIED

A result must be re-creatable on an engine that didn't produce it, by content transfer or by recomputation — at least one retained path, both when possible (some recipes are legitimately not retainable). Materializing a result must not destroy its recipe; persisting a result must be able to carry value, recipe, or both.

R2 — No stranded hits CARRIED

Adopting a result as a cache hit is a promise: the result will materialize on demand via some retained source, or the adoption itself was a bug. Preferred-source failure falls through to the next source. Silent wrong answers and use-time "missing snapshot" errors are design failures.

R3 — Portable semantic identity CARRIED

Every identity that crosses an engine boundary (persistence file, export bundle, backend row) is either a semantic digest or a durable origin identity. Engine-local allocator IDs never serialize. Importing the same result twice is idempotent.

R4 — Content-addressed snapshot identity, lazy at export CARRIED

Immutable snapshot content crossing any boundary is identified by its content (layer diffID chains), never by local snapshotter keys. Mutable-owner snapshots never cross boundaries as content. Hard constraint: content identity is computed lazily at export time (hash-while-packing), never eagerly during normal execution — eager content-hashing is a previously-hit, real performance trap.

R5 — Materialization state: one home per result, surgery-proof REWRITTEN

Every result's materialization state (materialized / remotely materializable / recomputable, plus the content itself once present) has exactly one home, owned by the cache, keyed by the result. It is written only at well-defined points — publication of locally-completed work, lazy content arrival for that result, import — under the cache's ordinary locking. Clones, copies, detached views, and mount-replay reference the home (so they can never strand or drop capability); they never copy its state and never acquire homes of their own. Content state is never shared across results: if two equivalent results both have content, that is tolerated redundancy for GC, not a consistency problem to reconcile.

R6 — Explicit execution identity CARRIED

Deferred/recomputed work runs under an explicit principal (the forcing waiter's), with retry on principal death; the identity of a result is fully determined by its recipe and never contaminated by whoever forced materialization.

R7 — Session-resource soundness extends to foreign results CARRIED

An adopted result that transitively requires secret/socket handles is only adoptable by sessions holding those handles — same rule as today, surviving import. (The known per-engine secret-salt issue remains deliberately deferred and separately tracked; it partitions caches across engines until addressed.)

R8 — Falsifiable observability CARRIED

Every lookup outcome, adoption decision, materialization-source execution, and fallback is observable with structured vocabulary; every run can produce a reuse summary; proofs and tests can turn unexpected outcomes into hard failures. Landings are validated against pre-registered, falsifiable predictions (state what the evidence must show before running the test), and forensic diagnostics that earn their keep at a failure site are made permanent rather than left as temporary instruments.

R9 — One portable result encoding CARRIED

Local persistence and remote export share one encoding for results (frames, payload envelopes, snapshot links, recipes). The surrounding structure differs by design: local persistence may additionally dump engine-local index rows for fast same-engine restart — subject to R16 — while bundles carry none of that. No second, looser result-serialization model.

R10 — Identity-stable metadata CARRIED

Import → re-export cycles add zero result rows. Genuinely new executions add honestly-new rows; independently-produced equivalents remain distinct rows related by semantic digests, and collapsing those for serving is backend merge policy on the digest layer — the engine's obligations are stable row identity, faithful digest emission, and a self-check metric.

R11 — In-repo provability, gated continuously CARRIED

The full adoption/hydration/fallback model is exercisable by integration tests inside dagger/dagger with no cloud stack. A curated integration set is a standing gate for every landed chunk of work, not a milestone-end event: anchors are the persistence/restart suite, the cross-session-caching tests, and a selection of the services tests; agents may add tests they judge valuable, within reason. Budget is deliberately not encoded as a number here — the full gate on the order of a quarter-hour is acceptable, focused subsets are for iteration, and the owner monitors actual costs. Legitimate intermediate failures are named, temporary, owner-acknowledged exceptions.

R12 — Sparse, demand-bounded materialization CARRIED

Materializing a result moves and creates only what is strictly required: the content path touches exactly the needed chain blobs; the recipe path recurses only into the inputs the recipe actually reads, itself demand-driven; adoption, viability, and import are metadata-only and move zero content. The canonical scenario: a huge tangled DAG culminating in one result — a warm run that reads one file from it hydrates that file's chain and nothing else.

Granularity clarification (owner-ruled). The load-bearing floor is: materializing a result must never require materializing its dependency DAG. Granularity within a single result is deliberately open: for a multi-output result (e.g. an exec's filesystem + its stdout/exit metadata), materializing outputs individually and materializing them together are both acceptable — choose whichever is simpler and more cohesive. The recipe path already materializes all of a result's outputs together, so insisting on per-output granularity for the content path creates an asymmetry between the two paths — don't pay complexity for that without a strong, stated reason. A design-time consideration (not a requirement): very small outputs (exit codes, small streams) may simply live in metadata rather than participate in content materialization at all.

R13 — Recipes are closed over engine-ambient state CARRIED

Any engine-local input that shapes a result — native platform, the engine secret salt, engine/schema version, anything read off server state during planning or resolution — must either be canonicalized into the recipe (so equivalent work matches and different work partitions) or explicitly partition the cache. Identity that silently depends on which engine ran the call fails silently: wrong adoptions or permanent misses.

R14 — Startup-only import; the serving-time cache is read-mostly NEW

All bulk ingestion of identity and result metadata — disk restore and remote bundle import — completes before the engine serves sessions, under coarse locking (these are fast, batched metadata writes; there is no pause-time problem to engineer around). While serving, cache state changes only through publication of locally-completed work and lazy content arrival on a result's own home (R5). Continuous / mid-serving import is an explicit non-goal for this take; if a future take adds it, it arrives with its own explicit quiesce design and may not weaken R15 to do so.

R15 — No new cross-cutting concurrency invariants NEW

The design builds on the engine's existing locking and singleflight structure, and this document is the source of truth for its concurrency model. The strong default: no new cross-cutting concurrency invariants — reader-audience classifications, run-scoped transactions or overlays over shared state, multi-lock protocols spanning packages. Working test: if a proposed mechanism requires auditing "every reader / every writer / every entry point" to be correct, treat that as a tripwire — stop, escalate, and discuss before building.

Two clarifications so this constraint cuts where intended. First, it does not forbid ordinary, contained engineering: adding a mutex around a data structure, a singleflight on a call path, or similar locally-reasoned synchronization is normal work, not an exception to this requirement. Second, this is a design constraint, not a taboo: if a cross-cutting mechanism ever appears genuinely necessary, the path is to make the case, get explicit agreement, and write it into this design before implementation — necessity and agreement are both required, and any such proposal should be treated with the utmost suspicion precisely because this class of mechanism is where the previous attempt's complexity came from. Interchangeability of equivalents, specifically, is a decision-point policy (pick a winner at lookup), never continuous reconciliation of shared mutable state.

R16 — Restart-deterministic lookup identity NEW

Warm lookup keys are a pure function of persisted, content-addressed identity — a restarted (or foreign) engine derives identical keys for identical calls regardless of in-memory assignment order, timing, or concurrent load. Any key component derived from memory-assigned ordinals (class numbers, allocator IDs, insertion order) is either recomputed canonically from persisted digests on load or never participates in persisted identity at all. This is cheaply testable as a property (boot a fresh engine on persisted state, derive keys, compare) — a determinism test, not an integration saga.

Clarification — what "identical calls" means here. The engine deliberately supports identity scoped narrower than content: per-client, per-session, and per-call inputs exist on purpose, make two calls genuinely non-identical across engines (or across sessions), and are fully legal under this requirement — they simply never produce cross-engine key matches themselves, and results downstream of them that acquire content-addressed identity are where sharing resumes, by design. R16 constrains only accidental divergence: bookkeeping artifacts leaking into the keys of calls that are semantically identical. Deliberate cache partitioning is a feature; timing-dependent cache partitioning is the bug.

Corollary — Partial local persistence CARRIED

A deliberate local corollary of R1+R2+R5: local persistent cache stops being all-or-nothing. Today any inconsistency wipes the whole store; with per-result source state and adoption gating, a result whose snapshot was lost falls back to its recipe or is dropped (with its dependents), keeping the rest. A user-visible robustness win with zero remote-cache dependency — in scope (owner-confirmed); sequencing within the take is decided in Part II.

Explicit non-goals (this take) NON-GOALS

  • Live / continuous import while serving. Superseded by R14. Import happens at startup; later arrivals wait for the next boot (or a future, separately-designed quiesce).
  • Content interchangeability as a continuous runtime invariant. Superseded by R15 + R5. Equivalents are interchangeable at lookup time; nothing moves content between results after the fact.
  • Cross-result / cross-class sharing of content state (shared records, fill-if-absent reconciliation, live healing). Redundant content between equivalent results is acceptable and garbage-collectible.
  • Run-scoped transactional isolation over cache state (overlays, forks, commit/discard, reader-audience splits). With R5+R15 there is no mid-run shared state to isolate; runs build private values and publish once.
  • The remote service/transport itself. Out of this take entirely (§1); the engine work must only remain compatible with it.

6. Target shape (ratified round 4 — living, adjustable)

The one-screen picture of the system this design builds, stated mechanism-neutrally — every "how" here is owned by a later section, and two explicitly open questions are flagged rather than implied away.

The shape, in prose

  • Boot. The engine restores its local persisted state and imports any provided bundles before serving sessions, under coarse locking (R14). The identity index is rebuilt such that lookup keys are pure functions of persisted digests (R16) — no dependence on reconstruction order or timing.
  • Serving — lookups. A lookup consults the identity layer (the e-graph, unchanged from main) and resolves to at most one winning result. A winner whose content is not yet local is still a normal cache hit: its content materializes on demand via a retained source — local snapshot, content transfer (in the remote future), or recipe re-execution — falling through on failure (R1, R2), moving only what is demanded (R12).
  • Serving — publication. Completed local work appends results and teaches equivalence exactly as main does today. Content state is written once, to that result's single home (R5). Runs build private values; the cache never exposes in-progress state because there is none to expose.
  • Shutdown. Persisted state is flushed using the one portable result encoding (R9): per result, value, recipe, or both (R1).

Cross-section invariants

  • One content home per result; references, never copies (R5).
  • The cache mutates at decision points only: boot-import, publication, lazy content arrival, shutdown flush (R14, R15).
  • Lookup-key determinism across restart (R16).
  • No new cross-cutting concurrency machinery anywhere in the above (R15).

Explicitly open questions (owned by later sections, not decided here)

  • Is on-demand materialization of a restored result simply the engine's existing lazy-evaluation path? It might be — restored-result hydration and lazy evaluation have the same shape (a result whose value isn't computed yet, computed on first demand). If so, no new wait/claim machinery exists at all. If not, the content-home section must argue why and design the difference minimally. Deliberately undecided; nothing in this doc may presuppose either answer. → answered by §7 (draft, pending review).
  • Metadata growth under winner-at-lookup. Tolerating redundant content between equivalent results (GC instead of reconciliation) must be shown to satisfy R10 and R15 simultaneously — the content-home section carries an explicit metadata-growth model. → answered by §7 (draft, pending review).

7. The content home: result & materialization state (draft, under discussion)
Traces to: R5 (the home itself), R1/R2 (retained sources and fall-through), R12 (demand-bounded), R4 (what identities may appear where), R10 (growth model). Answers both open questions from §6, at the model level. Necessity: this is the state model everything else reads and writes; it is a consolidation of state that already exists scattered on main, not a new layer.

Current state on main (verified @ 672ce93530)

  • Content lives on value structs, in accessor cells. Directory{Lazy, Dir, Snapshot *LazyAccessor} (core/directory.go:43–51); Container{FS, MetaSnapshot *LazyAccessor, …} (core/container.go:62–78); exec result sources DirectorySource/FileSource (:437–439). Clones sometimes copy cells (e.g. CloneContainerMetaSnapshot, core/container.go:906).
  • Persistence encodes a per-result envelope — typed payload plus snapshot references harvested from the value (encodePersistedResultEnvelope, dagql/cache_persistence_self.go:85; snapshotOwnerLinksFromTyped, :390). Snapshot references are local refKeys kept alive by leases — they never cross engine boundaries, consistent with R4's local carve-out.
  • Restored results already realize on demand. Deferred decode (ensurePersistedHitValueLoaded, dagql/cache_persistence_import.go:552) and value-level lazy evaluation on the result row — shared.lazyEval with its own singleflight/waiter machinery (dagql/cache.go:2895–3032) — which re-runs the value's Lazy closure (the recipe) with session attribution.
  • Failure handling is all-or-nothing. Schema mismatch, unclean shutdown, or any import failure resets the entire store (dagql/cache.go:98–101; engine/server/server.go:444–460, "resetting worker and dagql persistence state").
  • The R5 gaps, concretely: capability ("what does this result have; how can it be re-made") is implicit and scattered across envelope, cells, and closures; a cell copied before realization strands capability the row still has; a lost snapshot has no ordered fallback (stranded hit, or the full wipe above); and nothing states which writes are legal when.

Design

  1. The home lives on the cache's result row. Each result row (sharedResult) owns a materializationState: the persisted-form envelope, the ordered list of retained sources, and a realized flag for the in-memory value payload. Core value structs remain exactly what they are on main — plain data whose accessor cells are realization artifacts — but the row is the sole source of truth for capability. The row is written only at the decision points: publication (locally-completed work; sources recorded as available: local-snapshot, plus recipe when retainable), lazy content arrival (realization marks its own row realized), import (row created with envelope + sources, unrealized), and flush (reads). All under the cache's existing locking; no new locks (R15).
  2. Retained sources, in fall-through order (R1/R2): local-snapshot (local refKeys + leases; local-only identity per R4) → recipe (the frozen frame — the value's existing Lazy closure, made an explicit, persisted capability) → reserved seam: content-chain (R4 chainIDs, the remote future — named once here so fall-through order is designed once; not built this take). A row with zero viable sources is not servable as a hit (R2): at restore it is dropped along with its dependents — the partial-persistence behavior itself lands in the restore section.
  3. Open question 1, answered: on-demand materialization is the existing lazy-evaluation path. This is main's reality already — restored rows realize via deferred decode plus shared.lazyEval's existing singleflight — and the design keeps it. What changes is what the lazy work consults: the row's ordered sources, falling through on failure, instead of an implicit snapshot-or-closure choice. How waiting works does not change; no new wait/claim machinery exists (the shelved kernel stays shelved). Mechanism detail — source iteration, error taxonomy, what "viable" checks — is owned by the warm-lookup section.
  4. The surgery rule (R5). Accessor cells are realization caches, never capability records. A clone that copies a cell copies realized-state-or-absence, and absence is always recoverable through the row (a cell's GetOrEval already routes through its owner to the row's lazy path). No value-side write may create capability the row doesn't know about: persistence encodes from the row, not by harvesting value state — retiring the harvest-from-value pattern is a transition detail owned by the persistence section.
  5. Open question 2, answered: the metadata-growth model. Rows are created in exactly two ways: genuinely-new executions (honest growth, R10) and first-time import (idempotent by portable identity — re-import and import→re-export cycles add zero rows, R3/R10). Winner-at-lookup adds no rows and copies no content. Redundant content bytes between independently-executed equivalents are possible; they are bounded by real independent cold executions (exactly what sharing exists to make rare) and are reclaimed by normal prune as the losers' last-use ages out. Redundant metadata is just the loser rows themselves — which R10 requires to remain distinct anyway (related by digests; collapsing them for serving is backend merge policy, out of engine scope). No reconciliation, forwarding, or healing machinery exists to amplify anything. The persistence section adds R10's self-check metric.
  6. Deliberate non-additions: no cross-result sharing of any kind; no replacement of LazyAccessor (cells stay as they are — smallest change that satisfies R5; pointing cells into the row was considered and dropped absent a demonstrated need); no new locks; no eager content hashing anywhere (R4).

Implementation detail

This is consolidation, not addition: the row-side state that already exists in pieces — shared.lazyEval/lazyEvalComplete, the deferred-decode envelope handling, the harvested snapshot links — becomes one named structure.

Shelved: M0 — observability-first milestone

Why shelved (owner ruling, round 3): horse before cart. R8 remains fully in force — but each design section specifies the proof and observability it actually needs, with real consumers, when it is written. Building a standalone observability layer first means designing vocabulary and machinery against imagined consumers (the drafting history proved the point: its strict modes and forensics ring were cut in review for exactly that flaw before the whole milestone was shelved). A consolidated up-front observability pass may be re-decided at the end of the design, once every section's needs are known — that decision belongs there, not here.

Reconciliation note (kept with this entry): any observability built for this effort is process debugging tooling — built properly, but expected to reconcile with the parallel observability workstreams (OTel-based profiling / cache-performance analysis, in flight elsewhere) rather than outlive them as-is, and deliberately not entangled with them now, so this effort never ends up debugging that plumbing alongside its own.

The shelved draft, in useful-summary form (was grounded against main @ 672ce93530; main has only coarse EntryStats() (dagql/cache.go:3118), the debug snapshot writer (engine/server/server.go:869/:876), and span-level CachedAttr (core/telemetry.go:260)):

  • Outcome vocabulary — every cache lookup classifies its outcome exactly once, at the terminal paths of the lookup entry point (GetOrInitCall's return sites). Provisional terms: hit_live, hit_restored, miss_first; later work extends the enum (adoption, viability, sources) rather than adding a second reporting channel. The real payoff arrives when remote caching makes "what kind of hit was that?" a genuinely multi-valued question.
  • Per-field counters — engine-lifetime counters keyed (outcome, field). Field keying is what makes strong assertions safe: a warm engine legitimately first-misses session-scoped calls (R16's clarification), so proofs assert per named field, not globally.
  • Per-event debug log — one debug-level structured line per classification (outcome, field, call digest): the diagnosis path when a count assertion fails.
  • Surfaces — a small stats JSON written next to the persisted DB at clean shutdown (the test-assertion vehicle: files, not log streams); the same data folded into the existing debug snapshot; one INFO summary line at session close for humans.
  • Restored-origin marking — import-created rows marked so hits classify as hit_restored.
  • The concrete restart proof it was designed around: cold engine A runs a pipeline whose exec writes a random value; clean shutdown; warm engine B runs the identical pipeline; assert (1) outputs equal — which proves reuse only for the rigged random call, since deterministic outputs prove nothing about caching — and (2) from B's stats: hit_restored ≥ K and miss_first == 0 for the pipeline's named fields; diagnose failures by grepping the per-event log for those fields' misses.
  • Recorded cuts (review round 3, before shelving): strict modes (the concrete walkthrough showed per-field counter assertions + per-event logs deliver both the proof and the attribution; fail-at-the-call enforcement can return against a concrete consumer); the forensics ring (superseded by the per-event log — no new storage or endpoint); per-session tallies (no consumer — the proof harness boots dedicated engines, so per-engine counters are already per-test).

Shelved: M1 — shared wait/claim kernel (the "stage")

Why shelved (owner ruling, round 3): no consumer exists yet, and designing a concurrency primitive against hypothetical consumers is how policy knobs (sticky/retryable) appear before anything needs them. The draft was also, honestly, partly carry-over reflex from the previous take's equivalent. If a design section develops a real need, the mechanism gets designed there, with its consumer — and whether the existing hand-rolled protocols then migrate onto it is an explicit boilerplate-vs-abstraction decision (lesson L5) made at that point. Load-bearing open question recorded in §6: on-demand materialization of restored results may simply be the existing lazy-evaluation path — in which case no new wait/claim machinery ever exists. This shelf entry must not bias that question.

What the draft contained, kept as grounding for that future decision:

  • The pattern it targeted ("many callers wait on one deferred piece of work"), hand-rolled today in three places on main, each slightly different: ongoingCall's waitCh/waiters (dagql/cache.go:1745–1757); the lazy-evaluation protocol (dagql/cache.go:2802–3032) with last-waiter cleanup and ordering enforced by comment (":2977"); the restored-result dependency-attachment barrier (dagql/cache_persistence_import.go:563–576).
  • The primitive it proposed: an error-only "stage" (payloads live on the owning object, written before completion; the channel close provides the happens-before edge) with explicit waiter accounting, last-waiter cancellation with cause, caller-detached execution context, and two completion policies (freeze-first-outcome for publication; retry-on-failure for lazy evaluation and materialization). Its correctness pitch: no shared error observed outside the synchronization that produced it, and no ordering that lives in a comment.
  • The "claim" idea — N concurrent sessions racing to use a restored result whose content isn't materialized: one wins and materializes, others wait, failure releases so the next waiter retries the next source (R2's fall-through). This is the hypothetical consumer; it only becomes real if the warm-lookup design needs a mechanism distinct from lazy evaluation.
