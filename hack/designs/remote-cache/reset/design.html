1. The goal (unchanged)

A run on engine A executes a build graph; its cache results (metadata + content) become available to engine B, which adopts equivalent results as cache hits and materializes their content on demand — downloading snapshot content when available, re-executing the recipe when not. The near-term proof is unchanged: a cold CI run seeds the cache; a warm run on fresh engines shows a real, expected-scale improvement, with counters that demonstrate actual adoption and reuse — and that would have failed loudly if reuse hadn't happened.

The first concrete configuration of that goal is the restart case: one engine persists to disk, a fresh engine boots on that state and gets warm hits. It is the same problem as the remote case with the transport removed, and it is provable entirely in-repo (R11).

Scope of this take (owner-confirmed): engine changes only. The remote service/transport is not part of this batch of work — it stays in the goal statement above as the end state everything must remain compatible with, but nothing here designs or builds it.

2. The one structural shift this re-scope makes

The previous take coupled two layers that must stay separate. The engine's existing identity layer (the e-graph: equivalence classes over calls/results, merged live as work completes) was extended so that content state (filesystem snapshots, metadata, materialization status) was shared across equivalence classes and reconciled continuously — any equivalent result could serve any sibling's content at any moment, including mid-run. Protecting running work from that live movement required a transactional machinery (run-private overlays, reader-audience classification, evaluation gates, instance binding, three interacting locks) whose correctness surface was every reader, writer, and entry point in the engine. That machinery generated its own bug supply and consumed the effort.

The re-scope keeps the identity layer exactly as it is on main, and demotes interchangeability from a continuous runtime invariant to a decision-point policy: equivalence is consulted when it matters — at lookup (pick one winner and materialize that result), at publication, at import — and content state has exactly one home per result, mutated only at well-defined points under ordinary locking. Runs build private values, as they do on main today, and touch the cache only when they publish.

3. Carried requirements, re-adjudicated

Original text is condensed but faithful; the verbatim originals are in ../01-engine-baseline-design.md §1 (previous take's worktree). Badges: KEEP unchanged · MODIFY rewritten below · DROP removed.

R1 — Dual materialization paths KEEP

ORIGINAL
A result must be re-creatable on an engine that didn't produce it, by content transfer or by recomputation — at least one retained path, both when possible (some recipes are legitimately not retainable). Materializing a result must not destroy its recipe; persisting a result must be able to carry value, recipe, or both.

VERDICT — Keep unchanged. This is the heart of a lazy remote cache and played no part in the complexity failure.

R2 — No stranded hits KEEP

ORIGINAL
Adopting a result as a cache hit is a promise: it will materialize on demand via some retained source, or the adoption itself was a bug. Preferred-source failure falls through to the next source. Silent wrong answers and use-time "missing snapshot" errors are design failures.

VERDICT — Keep unchanged. The essence of correctness for the whole feature.

R3 — Portable semantic identity KEEP

ORIGINAL
Every identity that crosses an engine boundary (persistence file, export bundle, backend row) is either a semantic digest or a durable origin identity. Engine-local allocator IDs never serialize. Importing the same result twice is idempotent.

VERDICT — Keep unchanged. Validated in practice; the identity/portability layer was not where the trouble came from.

R4 — Content-addressed snapshot identity, lazy at export KEEP

ORIGINAL
Immutable snapshot content crossing any boundary is identified by its content (layer diffID chains), never by local snapshotter keys. Mutable-owner snapshots never cross boundaries as content. Hard constraint: content identity is computed lazily at export time (hash-while-packing), never eagerly during normal execution — eager content-hashing is a previously-hit, real performance trap.

VERDICT — Keep unchanged, including the anti-requirement on eager hashing.

R5 — Materialization state: one home per result, surgery-proof MODIFY

ORIGINAL
Materialization state is cache-owned and surgery-proof: whether a slot of a result is materialized, remotely materializable, or recomputable is a fact the cache owns per result. Object cloning/copying/mount-replay cannot silently strand or drop that capability — attached or detached.

VERDICT — Keep the intent, rewrite the text. As written, "the cache owns state per result" licensed an escalation: cache-owned records → records shared across equivalence classes → live reconciliation → the overlay/transaction machinery. The valid core is narrower and must say so explicitly.

REWRITE (R5')
Every result's materialization state (materialized / remotely materializable / recomputable, plus the content itself once present) has exactly one home, owned by the cache, keyed by the result. It is written only at well-defined points — publication of locally-completed work, lazy content arrival for that result, import — under the cache's ordinary locking. Clones, copies, detached views, and mount-replay reference the home (so they can never strand or drop capability); they never copy its state and never acquire homes of their own. Content state is never shared across results: if two equivalent results both have content, that is tolerated redundancy for GC, not a consistency problem to reconcile.

R6 — Explicit execution identity KEEP

ORIGINAL
Deferred/recomputed work runs under an explicit principal (the forcing waiter's), with retry on principal death; the identity of a result is fully determined by its recipe and never contaminated by whoever forced materialization.

VERDICT — Keep unchanged.

R7 — Session-resource soundness extends to foreign results KEEP

ORIGINAL
An adopted result that transitively requires secret/socket handles is only adoptable by sessions holding those handles — same rule as today, surviving import.

VERDICT — Keep unchanged. (The known per-engine secret-salt issue remains a deliberately deferred, separately-tracked item, as before; it partitions caches across engines until addressed.)

R8 — Falsifiable observability KEEP + STRENGTHEN

ORIGINAL
Every lookup outcome, adoption decision, materialization-source execution, and fallback is observable with structured vocabulary; every run can produce a reuse summary; strict modes turn unexpected fallback/recompute into hard failures for proofs and tests.

VERDICT — Keep, and add one sentence the previous take proved out: landings are validated against pre-registered, falsifiable predictions (state what the counters must show before running the test), and forensic diagnostics that earn their keep at a failure site are made permanent, not left as temporary instruments.

R9 — One portable result encoding KEEP

ORIGINAL
Local persistence and remote export share one encoding for results (frames, payload envelopes, snapshot links, recipes). Local persistence may additionally dump engine-local index rows for fast same-engine restart; bundles carry none of that. No second, looser result-serialization model.

VERDICT — Keep unchanged, with one cross-reference: whatever engine-local index rows are persisted must satisfy the new R16 (a restarted engine must not depend on in-memory numbering to reproduce lookup keys).

R10 — Identity-stable metadata KEEP

ORIGINAL
Import → re-export cycles add zero result rows. Genuinely new executions add honestly-new rows; independently-produced equivalents remain distinct rows related by semantic digests; collapsing those for serving is backend merge policy on the digest layer.

VERDICT — Keep unchanged. Note how well this sits with the structural shift: "equivalents remain distinct rows related by digests" was already the right philosophy — the previous take's content layer just didn't follow it.

R11 — In-repo provability KEEP + STRENGTHEN

ORIGINAL
The full adoption/hydration/fallback model is exercisable by integration tests inside dagger/dagger with no cloud stack.

VERDICT — Keep, strengthened per lesson L2: a curated integration set is a standing gate for every landed chunk, not a milestone-end event. Legitimate intermediate failures are named, temporary, owner-acknowledged exceptions. Anchor membership (per owner review): the persistence/restart suite; the cross-session-caching tests (a consistent naming pattern across several suites — they exercise tricky caching scenarios including modules); a selection of the services tests. Agents may add tests they judge valuable, within reason. Budget is deliberately not encoded as a number here: the full gate on the order of a quarter-hour is acceptable, focused subsets are what you run while iterating, and the owner monitors actual costs — no mechanical timeout to game or trip over.

R12 — Sparse, demand-bounded materialization KEEP

ORIGINAL
Materializing a slot moves and creates only what that slot strictly requires: the content path touches exactly that slot's chain blobs; the recipe path recurses only into inputs the recipe actually reads, itself demand-driven; adoption, viability, and import are metadata-only and move zero content. Canonical scenario: a huge tangled DAG culminating in one result — a warm run that reads one file hydrates that file's chain and nothing else.

VERDICT — Keep, with one granularity clarification. The load-bearing floor of this requirement is: materializing a result must never require materializing its dependency DAG. Granularity within a single result is deliberately left open: for a multi-output result (e.g. an exec's filesystem + its stdout/exit metadata), materializing outputs individually and materializing them together are both acceptable — choose whichever is simpler and most cohesive with the system. Note the recipe path already materializes all of a result's outputs together (running the exec produces everything at once), so insisting on per-output granularity for the content path creates an asymmetry between the two paths — don't pay complexity for that symmetry break without a strong, stated reason. One design-time consideration to weigh when the time comes (not a requirement): very small outputs (exit codes, small streams) may simply live in metadata rather than participate in content materialization at all, which sidesteps the granularity question for the common "read exit code without pulling a large filesystem" case.

R13 — Recipes are closed over engine-ambient state KEEP

ORIGINAL
Any engine-local input that shapes a result — native platform, engine secret salt, engine/schema version, anything read off server state during planning or resolution — is either canonicalized into the recipe or explicitly partitions the cache. Identity that silently depends on which engine ran the call fails silently: wrong adoptions or permanent misses.

VERDICT — Keep unchanged (the ambient-state audit from the previous take remains valid input material for the new architecture part).

Corollary — Partial local persistence KEEP

ORIGINAL
Local persistent cache stops being all-or-nothing: today any inconsistency wipes the whole store; with per-result source state and adoption gating, a result whose snapshot was lost falls back to its recipe or is dropped (with its dependents), keeping the rest.

VERDICT — Keep. A user-visible robustness win that falls straight out of R1+R2+R5', with zero remote-cache dependency.

4. New requirements

R14 — Startup-only import; the serving-time cache is read-mostly NEW

All bulk ingestion of identity and result metadata — disk restore and remote bundle import — completes before the engine serves sessions, under coarse locking (these are fast, batched metadata writes; there is no pause-time problem to engineer around). While serving, cache state changes only through publication of locally-completed work and lazy content arrival on a result's own home (R5'). Continuous / mid-serving import is an explicit non-goal for this take; if a future take adds it, it arrives with its own explicit quiesce design and may not weaken R15 to do so.

R15 — No new cross-cutting concurrency invariants (the simplicity ratchet) NEW

The design builds on the engine's existing locking and singleflight structure, and this document is the source of truth for its concurrency model. The strong default: no new cross-cutting concurrency invariants — reader-audience classifications, run-scoped transactions or overlays over shared state, multi-lock protocols spanning packages. Working test: if a proposed mechanism requires auditing "every reader / every writer / every entry point" to be correct, treat that as a tripwire — stop, escalate, and discuss before building.

Two clarifications so this constraint cuts where intended. First, it does not forbid ordinary, contained engineering: adding a mutex around a data structure, a singleflight on a call path, or similar locally-reasoned synchronization is normal work, not an exception to this requirement. Second, this is a design constraint, not a taboo: if a cross-cutting mechanism ever appears genuinely necessary, the path is to make the case, get explicit agreement, and write it into this design before implementation — necessity and agreement are both required, and any such proposal should be treated with the utmost suspicion precisely because this class of mechanism is where the previous attempt's complexity came from. Interchangeability of equivalents, specifically, is a decision-point policy (pick a winner at lookup), never continuous reconciliation of shared mutable state.

R16 — Restart-deterministic lookup identity NEW

Warm lookup keys are a pure function of persisted, content-addressed identity — a restarted (or foreign) engine derives identical keys for identical calls regardless of in-memory assignment order, timing, or concurrent load. Any key component derived from memory-assigned ordinals (class numbers, allocator IDs, insertion order) is either recomputed canonically from persisted digests on load or never participates in persisted identity at all. This is cheaply testable as a property (boot a fresh engine on persisted state, derive keys, compare) — a determinism test, not an integration saga.

Clarification — what "identical calls" means here. The engine deliberately supports identity scoped narrower than content: per-client, per-session, and per-call inputs exist on purpose, make two calls genuinely non-identical across engines (or across sessions), and are fully legal under this requirement — they simply never produce cross-engine key matches themselves, and results downstream of them that acquire content-addressed identity are where sharing resumes, by design. R16 constrains only accidental divergence: bookkeeping artifacts leaking into the keys of calls that are semantically identical. Deliberate cache partitioning is a feature; timing-dependent cache partitioning is the bug.

Ratified in review round 2, justified on first principles (warm hits must not depend on when in-memory bookkeeping catches up). One-line provenance: a previous-take observation pointed here, but was never root-caused and is deliberately not load-bearing — the new architecture must satisfy this by construction, not by fixing that observation.

5. Explicit non-goals (this take)

Removed from scope NON-GOALS

  • Live / continuous import while serving. Superseded by R14. Import happens at startup; later arrivals wait for the next boot (or a future, separately-designed quiesce).
  • Content interchangeability as a continuous runtime invariant. Superseded by R15 + R5'. Equivalents are interchangeable at lookup time; nothing moves content between results after the fact.
  • Cross-result / cross-class sharing of content state (shared records, fill-if-absent reconciliation, live healing). Redundant content between equivalent results is acceptable and garbage-collectible.
  • Run-scoped transactional isolation over cache state (overlays, forks, commit/discard, reader-audience splits). With R5'+R15 there is no mid-run shared state to isolate; runs build private values and publish once.

M0 — Cache observability: outcomes, summaries, strict modes

Goal & traceability

Before any caching behavior changes, the engine can explain its cache decisions and prove claims about them: every cache lookup classifies its outcome exactly once against a small structured vocabulary; every session can produce a reuse summary; strict modes convert unexpected outcomes into loud failures at the offending call. M0 changes no caching behavior — observability only.

Traces to: R8 directly; R11 (the standing gates assert on these counters); every later milestone's pre-registered predictions are expressed in this vocabulary. Necessity: nothing like it exists on main (verified below); a bare log line would not give assertable counters or strict enforcement; the mechanism is contained to one new file plus classification at one function's terminal paths.

Current state on main

  • Cache.EntryStats() — coarse totals only (ongoing/completed/retained counts), dagql/cache.go:3118.
  • A cache/e-graph debug snapshot writer exposed through the server: engine/server/server.go:869 (DagqlDebugSnapshot) and :876 (WriteDagqlCacheDebugSnapshot).
  • Span-level telemetry.CachedAttr set when a call is served from cache (core/telemetry.go:260) — per-span, not aggregable, no miss/restored detail.
  • Not present anywhere: per-lookup outcome classification, restored-vs-live hit distinction, per-session aggregation or summary, strict modes.

Design

  1. Outcome vocabulary — deliberately tiny at M0; later milestones extend this enum as they create new paths (adoption, viability, materialization sources) and may not invent a second reporting channel:
    • hit_live — served from a result created during this engine process's lifetime;
    • hit_restored — served from a result restored from persisted state at startup;
    • miss_first — no candidate existed; the work executed.
    Classification happens at the terminal paths of the lookup entry point (GetOrInitCall's few return sites), not sprinkled across call sites — the "exactly once per lookup" property holds by construction at a decision point (lesson L5's preferred shape, and here it is clean).
  2. Counters and per-session tallies. Engine-lifetime atomic counters keyed (outcome, field); a bounded per-session tally created on first classification for a session and emitted-then-dropped at session close.
  3. Reuse summary. One structured, stable, grep-able log line at session close — cache summary session=… hit_live=… hit_restored=… miss_first=… — and the same data included in the debug snapshot output.
  4. Strict modes. A policy seam evaluated inside classification. M0 ships the seam plus the one mode the restart proof needs: _DAGGER_CACHE_STRICT=warm-no-first-miss — on an engine booted with it, any miss_first fails that lookup with a structured error naming the call. An optional _DAGGER_CACHE_STRICT_FIELDS=<csv> narrows enforcement to named fields, because a warm engine legitimately first-misses session-scoped calls (per-client/session/call inputs — see R16's clarification); tests name the calls that must hit. Deliberately crude (engine-level env, set by the test on the warm engine of a restart pair); richer scoping only if a real need appears.
  5. Restored-origin marking. Results created by the persistence-import path carry origin=restored on their in-memory row so hits classify correctly. No effect on identity or behavior.
  6. Forensics ring. A bounded ring (last 512 classified events with field + session) included in the debug snapshot — first-line evidence without a re-run.

M1 — The stage primitive: one wait/claim kernel

Goal & traceability

One tested kernel for "many callers wait on one deferred piece of work" under the cache — explicit waiter accounting, last-waiter cancellation with cause, caller-detached execution context, sticky vs retryable completion — replacing the hand-rolled per-site protocols main carries today. M1 is a behavior-preserving consolidation; it is also, deliberately, the concurrency kernel the architecture part's warm-lookup path (claim → materialize → fall through, R2) will be built on.

Traces to: R2 (the future claim/release/retry kernel must be sound once, not re-proven per site), R6 (caller-detached execution and principal-independent identity are properties of the primitive, tested once), R15 (net-negative invariant count: it deletes hand-rolled protocols). Necessity, honestly stated: the primary justification is what gets built on it; if the architecture part's review concludes its lookup path doesn't need this kernel, M1 shrinks to optional cleanup and must be re-justified rather than defended. Standing alone it still pays down verified risk — three divergent protocols, one relying on comment-enforced ordering.

Current state on main — the protocols being replaced

  1. In-flight call execution/publication: ongoingCall with waitCh chan struct{} + waiters int (dagql/cache.go:1745–1757, constructed ~:1983).
  2. Lazy evaluation: lazyEvalWaitCh + lazyEvalWaiters + waitForLazyEvaluation (dagql/cache.go:2802–3032) — with last-waiter cleanup conditions (lazyEvalWaiters == 0 && lazyEvalWaitCh == waitCh) and ordering enforced by comment ("End resumeSpan before close(waitCh)…", :2977).
  3. Dependency-attachment barrier for restored results: attachDepsMu/attachDepsWaitCh/attachDepsErr (dagql/cache_persistence_import.go:563–576).

The implementation audit may find further instances of the pattern; each either migrates or documents why not.

Design

The stage is error-only by design: payloads live on the owning object, written by the run before completion; waiters read them only after observing completion, so the channel close provides the happens-before edge. No type parameter, no payload plumbing. The correctness property that motivates the whole primitive: run.err is written before close(run.done), and waiters read the outcome only after <-done — there is no shared error field observed outside the synchronization that produced it, and no ordering that lives in a comment.

  • Two completion policies. Sticky: the first outcome, success or failure, is frozen — publication semantics (a produced result is a one-time fact). Retryable: success freezes; a failed run returns the stage to idle so a later caller re-runs — lazy evaluation today; decode and materialization later.
  • Protocol. begin joins the current run, starts a new one (the starter then calls launch), or observes a frozen outcome; every caller awaits; every begin pairs with exactly one leave (leaving room for per-waiter post-work between the two); the last waiter to leave an unfinished run cancels it with a cause and detaches it.
  • Producer-barrier variant. openBarrier/awaitIfPresent for the attach-deps shape: a single producer resolves the barrier; readers wait passively and never cancel the producer.

Implementation detail

// dagql/cache_stage.go (new)

type stageResetPolicy uint8

const (
	// stageSticky freezes the first completed outcome, success or failure.
	// Publication: a produced result is a one-time fact.
	stageSticky stageResetPolicy = iota
	// stageRetryable freezes success; a failed run leaves the stage idle so
	// the next join starts a fresh run. Lazy evaluation now; decode and
	// materialization later.
	stageRetryable
)

// begin joins the stage's current run, starts a new one (state ==
// stageJoinStarter — the caller must then launch), or reports a frozen
// outcome. prepare runs under the stage lock with the run's caller-detached
// base context and returns the context the work will execute under.
func (s *stage) begin(ctx context.Context, prepare func(run *stageRun, base context.Context) context.Context) (state stageJoinState, run *stageRun, frozenErr error)

// launch executes work on a goroutine under the run's caller-detached context.
func (s *stage) launch(run *stageRun, work func(runCtx context.Context) error)

// await blocks until the run completes or ctx is cancelled. It never touches
// waiter accounting — every begin pairs with exactly one leave.
func (s *stage) await(ctx context.Context, run *stageRun) (err error, completed bool)

// leave decrements the waiter count; the last waiter leaving an unfinished
// run cancels it with cause and detaches it so the next caller starts fresh.
func (s *stage) leave(run *stageRun, cause error) (wasLast bool)

Migration order — simplest first, each step independently landable and gated:

  1. attach-deps barrier → openBarrier/awaitIfPresent (pure barrier; no cancellation semantics to preserve);
  2. ongoingCall → sticky stage: the singleflight rendezvous (the map and callsMu) stays exactly where it is — the stage replaces only the waitCh/waiters/error tuple and the execution/outcome handoff;
  3. lazy evaluation → retryable stage: the delicate one — preserves last-waiter-cancel and retry-on-failure, and makes the span-ordering requirement structural (completion closes done after the run's teardown work) instead of comment-enforced.

Explicitly not in M1: the claim/reservation wiring for adoption. Its consumer doesn't exist until the architecture part; the primitive is shaped so a per-result retryable stage composes into claim/winner-runs semantics, and it is listed here strictly as the intended consumer. Building it now would violate the scoping discipline this reset exists to enforce.
