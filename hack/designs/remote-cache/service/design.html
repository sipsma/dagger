Remote Cache — Service Phase Design

v3  ·  the phase after the engine fundamentals  ·  review rounds 1–2 folded  ·  2026-07-06

Status. Converged through three adversarial review rounds (verdict: ready — §4); awaiting program-owner review. This document designs the phase that follows the engine-fundamentals take (hack/designs/remote-cache/reset/design.html, "the reset design"): engines exporting cache to and importing cache from a real cloud service. It builds on the reset design's ratified requirements R1–R16 and its reserved seams; any deviation from a reserved seam is stop-and-discuss, never silent — one such item is open: the §9.1 source-order amendment to the reset design, ratification-gated before chunk B. Engine-side code references are grounded against the take-3 integration branch (reset §7 + §8a–c merged); prior-attempt artifacts are cited as evidence about those attempts, never as precedent (§4, round 0; dispositions in §16).

1. The goal

A run on engine A executes a build graph. When engine A is told to — or when it shuts down — it exports its cache to a cloud cache service: the result metadata, and the filesystem content behind it. A fresh engine B, booting later with credentials for the same cache scope, imports that cache before serving: warm lookups hit, and content downloads on demand, falling back to re-execution where content is missing. The near-term proof is the remote analogue of the reset design's restart proof: a cold CI run on one engine seeds the service; a warm run on a different, fresh engine shows real, counter-proven reuse — with numbers that would have failed loudly if reuse hadn't happened (R8).

The reset design proved this shape with the transport removed (one engine's disk, a restart). This phase adds the transport and the service — and deliberately nothing else: the engine's lookup, vetting, materialization, and fallback machinery is consumed as built, not redesigned.

Scope of this phase:

  • Engine (dagger/dagger): the export path (trigger, bundle encode, blob upload), the bundle import path at boot, and the content-chain materialization source — the third retained source the reset design named and reserved (reset §7 D2, Fig. 4) and explicitly left for "the remote take".
  • Service (dagger.io, proprietary): bundle storage, a digest-addressed blob store, bundle selection for booting engines, lifecycle integration with cloud-managed engines, and real insight surfaces ("I need visualizations, I need to understand the cache, the state of it").
  • Proof: integration tests in dagger/dagger requiring no cloud stack (R11), an end-to-end suite in dagger.io that stands up the whole stack inside Dagger, and a live warm proof on cloud-managed engines as the final, credential-gated step.

Explicitly deferred cleverness: analysis-guided export policy (deciding what is worth exporting from run history) is out of scope. The seams where it will plug in are named (§7's export policy hook; §10's service-side bundle selection), and nothing in this design blocks it — but v1 policy is deliberately simple (§7 D3).

2. The load-bearing structural decision

The service stores; the engine merges. The cache service never parses, merges, or rewrites engine cache state. It stores opaque, engine-versioned bundles (one export = one bundle: a metadata artifact plus a manifest), keeps a digest-addressed blob store (CAS) for filesystem content, and answers exactly one clever question: "which bundles should this engine import?" All cache semantics — identity, equivalence, dedup, vetting, retention — run inside the engine's existing boot import, which the reset design already specifies as "restore local persisted state + import provided bundles" (reset §6, Fig. 2). The engine is the only component that understands cache state, and it already contains the entire machinery this job needs: per-result vetting (reset §8 D2), restart-deterministic key recomputation (R16), the e-graph for cross-source equivalence, and the session-resource gate (R7).

The tempting alternative is named here so it stays dead: a merging service — the service internally maintains cache state (in whatever form: an embedded engine cache, its own result tables), merges each incoming export into it, and synthesizes merged state for importers. Its structural costs are intrinsic, not implementation accidents:

  • It duplicates the engine's identity model on the server — every subtlety (equivalence classes, congruence, result-row identity, session-resource gating) needs a second, server-side life, and every divergence between the two lives is a correctness bug with a fleet-wide blast radius. Row identity is the sharpest instance: a merge layer that mints its own row identities on ingest turns import→re-export cycles into compounding metadata growth. (The evidence that this failure mode is real and terminal, not hypothetical, is recorded in the salvage ledger, §16.)
  • It couples the service to the engine's schema at the row level. A service whose internal state is engine cache state must be redeployed — or flushed — on every engine schema change; "the API evolves behind the wire protocol" is unachievable from that position by construction.
  • It makes service state load-bearing and expensive. Merged state must either be durable (a second persistence model for the same data) or in-memory (every service restart costs a full re-seed of the fleet's cache).

With store-and-select, each of those costs structurally disappears rather than being managed: there are no service-side result rows to blow up; the service treats bundle contents as opaque bytes tagged with an engine schema version, so engine schema evolution never touches it; and service state is a bundle inventory plus a CAS — trivially durable in Postgres + object storage, trivially disposable (it is a cache). The price is paid at engine boot: an engine may download and merge K overlapping bundles instead of one pre-merged view. That price is bounded and paid in the right place — bundle metadata is small relative to content, import is batched metadata writes under the boot lock (R14: "these are fast; there is no pause-time problem to engineer around"), and overlap collapses via origin-keyed dedup (§6) inside the one component that owns identity.

One deliberate nuance keeps Erik's insight requirement honest without reopening the coupling: the service may read bundles — a read-only indexer parses manifests and metadata for the insight surfaces (§11) — but the serving path never depends on it. Insight parsing is best-effort per engine schema version and degrades gracefully on unknown versions; the store/select/serve path treats bundles as bytes always. Reading for visibility is not merging for correctness, and the boundary is enforced by construction: the indexer has no write path into bundle or blob state.

3. Requirements and non-goals

Normative. S-numbers are this phase's requirements; R-numbers cite the reset design's ratified requirements, all of which remain in force. Adjudication history lives in the review log (§4).

S1 — Reset-design compatibility, by consumption

This phase plugs into the engine fundamentals; it never re-opens them.

The phase consumes the reset design's machinery as built: the content home and source walk (reset §7/§9), per-result vetting (reset §8 D2), R16 key recomputation, the demote-to-miss floor, and the session-resource gate. The one engine seam it builds is the one reserved for it: the content-chain source (reset §7 D2's source ③). Changes to reset-designed behavior beyond that seam are stop-and-discuss with the take-3 owner, never silent.

S2 — Idempotent, origin-keyed import

Importing the same bundle twice — or the same result via two bundles — adds zero rows, ever.

Every exported result row carries a durable origin identity minted exactly once, at the store where the result was first created, and preserved verbatim through every import/re-export hop. Import dedups by origin identity: a row whose origin is already present is not re-created (its metadata may be refreshed). The red test exists from day one: import the same bundle twice ⇒ zero growth (T-S2). This implements R3's "durable origin identity" and R10's zero-growth cycles across the engine boundary.

S3 — Multi-cycle growth bound, measured

Cold→warm→warm→warm must show flat metadata growth, proven by counters, not asserted.

The standing gate runs at least three consecutive export/import cycles over the same workload and requires the result-row count and bundle row count to stay flat modulo genuinely new executions (T-S3). Growth is a first-class observable (§11): the engine emits per-boot {rows_local, rows_imported, rows_deduped_by_origin}; the service reports per-scope bundle row counts over time. A consciously accepted growth debt without a measurement that screams is forbidden in this phase.

S4 — Cache traffic never breaks builds

The cache service is an accelerator. No export, import, or blob failure may fail a run that would otherwise be green.

Export failure never fails a green run (it is decoupled from run/check success and runs after it, or in the background). Import failure or timeout at boot degrades to cold start, bounded by a configurable budget. Blob-fetch failure at serving time falls through the source walk to the demote-to-miss floor (reset §9 D3) — the run computes honestly. Every such degradation is loudly counted (S8), never silently absorbed.

S5 — Correct under arbitrarily sparse blob availability

Metadata may promise content the store no longer has — and nothing breaks.

Blob availability is an optimization signal, never a correctness input. A bundle whose blobs are partially uploaded, partially GC'd, or entirely absent must produce only slower runs, not wrong ones: the content-chain source fails per-chain and falls through (recompute via the lazy form, or demote). This is what makes partial exports (S6) and service-side blob GC safe by construction, and it is exactly the behavior the reset design's runtime floor was built to provide.

S6 — Two-phase export: metadata commits, content streams

A bundle becomes visible only when its metadata is fully stored; blobs upload incrementally, and interruption loses bytes, not correctness.

Export publishes the metadata artifact atomically (a bundle is either fully present and listed, or absent). Blob upload proceeds independently — deduped against the CAS by digest, resumable, interruptible — and an interrupted upload leaves a valid bundle with sparser blob availability (S5). Export duration is therefore not a correctness deadline anywhere; how long uploads take is a measured cost (§11), not an inherited assumption.

S7 — Engine-schema-agnostic service

The service must not need a deploy when the engine's cache schema changes.

The serving path (store, select, hand out URLs) treats bundle metadata as opaque bytes tagged with the engine's persistence schema_version and the bundle format version. Engines request bundles matching their own versions; mismatched bundles are simply not offered (and age out via GC). Only the read-only insight indexer (§11) parses bundle contents, best-effort per known version. The engine's Go module may be imported for shared protocol types only — never for cache-state types.

S8 — Falsifiable observability, extended to the service

Every export, import, selection, blob fetch, and fallback is countable — and the proofs consume the counters.

R8 extends across the wire: the engine emits structured counters for export/import/fetch outcomes (including typed miss reasons — a session-resource/salt partition miss must be distinguishable from a plain miss); the service keeps a queryable event log and per-scope inventory. Every counter lands with a named consuming test or insight surface; none are decorative. Proof-of-reuse is by consequence (random-marker output equality) plus counters, never by proxy metrics like blob counts or green checks alone.

S9 — Credential-free development to the last step

Everything short of the live cloud deployment builds, runs, and proves itself without Erik's credentials.

The full stack — engine, service, blob store, lifecycle — must stand up inside Dagger with no external credentials: in-repo integration tests against a protocol-faithful test service (dagger/dagger), and an e2e suite in dagger.io that builds the real service handlers against containerized Postgres/MinIO and real dev engines. The only credential-gated step is the final live deployment to the managed dev stack (Namespace), and its runbook must assume credentials may be unavailable to agents: everything before it is the definition of buildable-and-testable.

S10 — No live secrets, no secret-derived content, in any bundle

Bundles carry handle-form dependencies only; the salt partition is explicit and observable.

Session resources cross the wire exactly as they cross local persistence: handle form only (the persisted envelope already guarantees this). The known per-engine secret-salt partition (reset R7's tracked deferral) remains deferred: results transitively requiring salted handles will not match across engines with different salts. This phase makes that partition visible (a typed miss/ineligibility counter, S8) and the harness workaround explicit (pre-seeding <rootDir>/secret-salt across test engines), but does not redesign salting — that remains a cloud/tenancy work item.

Explicit non-goals (this phase) NON-GOALS

  • A merging service. Superseded by §2. The service never composes or rewrites cache state; "smarter selection" is the sanctioned future path, "server-side merge" is not.
  • Analysis-guided export policy. The v1 policy is §7 D3; the policy hook is the seam. Learning what to export from run history is a later phase.
  • Mid-serving import. R14 stands: bundles import at boot, before serving. Engines that outlive many runs pick up new cache at their next boot.
  • Semantic (recipe-digest) row collapse. R10 keeps independently-produced equivalents as distinct rows; the e-graph already serves across them. Bounded semantic dedup is a recorded future optimization (§15), not v1 correctness.
  • Cross-engine secret-salt unification. Tracked deferral (S10).
  • Delta/incremental bundle formats. Bundles are whole snapshots of the retained store; blob upload is already delta-by-existence. Metadata delta encoding is an optimization for later, never a correctness requirement.
  • Open/self-hosted service protocol guarantees. The engine side is OSS and generic (any endpoint implementing the protocol works — the in-repo test service proves it), but v1 makes no protocol-stability promises to third parties.

5. Target shape

The one-screen picture, stated mechanism-neutrally; every "how" is owned by a later section.

The shape, in prose

  • Export. A configured engine, when signaled through its cache-admin API or when gracefully shutting down, snapshots its retained cache (the same snapshot machinery local flush uses), encodes it as a bundle — the one portable result encoding (R9) plus a manifest of content chains — publishes the metadata atomically to the service, then uploads whichever chain blobs the CAS is missing (S6).
  • Import. A booting engine asks the service for bundles matching its cache scope and schema version, downloads them, and merges them during the existing import-at-boot window (R14): per-result vetting, reference remapping into the local ID space, origin-keyed dedup (S2), R16 key recomputation. Imported results are ordinary rows afterward — they flush to local disk, prune normally, and survive local restarts.
  • Serve. The reset design's serving architecture, with one addition and one amendment: imported results carry a content-chain source — when the source walk reaches it, the engine fetches the chain's missing blobs from the CAS and applies them as snapshot layers, demand-bounded (R12), falling through on failure (S5) — and the source order places that chain ahead of the lazy form (the §9.1 amendment, ratification-gated).
  • The service. Stores bundles and blobs; selects bundles for booting engines; integrates with the managed-engine lifecycle (import at provision, export before teardown); exposes insight surfaces. It never composes cache state (§2).

Cross-section invariants

  • Identity semantics live only in the engine; the service serving path treats bundles as opaque (§2, S7).
  • Origin identity is minted once and preserved through every hop (S2); import is idempotent at every level (row, bundle, blob).
  • Blob availability is never a correctness input (S5); every degradation is a counted, typed event (S8).
  • All bulk metadata movement happens at boot or at export decision points; serving-time network I/O is only demand-driven blob fetch by the materialization write point (R14's sanctioned "content arrival").

6. The bundle: one portable cache artifact

The idea in three sentences. A bundle is one engine's retained cache state in the same encoding local persistence writes — the same envelopes, frames, and identity tables — minus the rows that are engine-local by definition (snapshotter refKeys, leases), plus the portable identity that replaces them: per-result origin identity and per-result content chains. Integer row IDs appear in a bundle only as intra-bundle join keys (exactly their role in the local file — reset §8 D1); the durable identity of every row is its origin pair. Import rewrites join keys into the local ID space at one decision point and dedups rows by origin, which is what makes cycles growth-free (S2, S3).

Names used from here on: the store UUID is a random identity minted when a persistence store is first created (stored in the meta table) and wiped with it; a result's origin is the pair (origin_store_uuid, origin_result_id) fixed at first publication; a chain is the ordered layer list (diffID + blob digest per layer) that reconstructs one immutable snapshot, identified by its containerd chainID (R4); the manifest is the bundle's small JSON header (versions, scope, roots, chains, blob index); the metadata DB is the bundle's SQLite artifact.

THE DECISIONS THIS SECTION MAKES
  1. Bundle = manifest + metadata DB in the local persistence encoding (R9's "one encoding", with the engine-local rows excluded and chains/origins added). No second serialization model.
  2. Row identity = origin pair, minted at first publication, persisted locally, and carried verbatim through every export/import hop (S2).
  3. Reference remapping is a decision-point rewrite at import: frame references via the existing structured walk; payload references via a structured ref token that replaces today's bare-integer encoding (a schema_version bump). The rejected alternatives are recorded below.
  4. What crosses and what doesn't: immutable snapshot content crosses as chains; mutable-owner snapshots and refKeys never cross (R4); session resources cross as handles only (S10).

6.1  What the local store already provides

The bundle design starts from what the take-3 store already writes at flush (dagql/persistdb/schema.sql): results (per result: the call frame JSON — identity and decode context — and the self_payload envelope carrying the value and/or its lazy fragment), the identity tables (eq_classes, eq_class_digests, terms, term_inputs, result_output_eq_classes), the graph tables (result_deps, persisted_edges), and the local-content tables (result_snapshot_links — snapshotter refKeys — plus the snapshot-manager metadata mirrors). Two facts matter:

Fact 1 — everything identity-bearing is already portable. After the take-3 R16 work, no persisted lookup key embeds in-memory ordinals: term keys are recomputed from digests at boot, and integer IDs in the file are joins, never identity (reset §8 D1). A bundle can therefore reuse the identity tables byte-for-byte: the importing engine already knows how to rebuild classes from digests and recompute keys in its own ID space — importPersistedState does exactly this for the local store today (dagql/cache_persistence_import.go:15, key recompute per reset §8 D1).

Fact 2 — exactly two things in the store are engine-local. The snapshotter refKeys (result_snapshot_links.ref_key, plus the snapshot-manager mirror tables keyed by snapshot IDs) and the store's integer ID spaces. The first is replaced in bundles by content chains (§6.4); the second is handled by the join-key + origin model (§6.2, §6.3).

6.2  D1 — Origin identity: minted once, carried forever

Every result row acquires an origin pair (origin_store_uuid, origin_result_id):

  • Minted at first publication. A locally-executed result's origin is (this store's UUID, its local result ID). Local result IDs are stable across flush/restore (import preserves file IDs 1:1 — cache_persistence_import.go:180, the sharedResult{id: resultID} construction) — but stability of surviving rows is not enough: after prune removes high rows and a clean restart resumes the allocator above the surviving maximum, an ID that was already exported could be re-allocated to a different result, and two results would claim one origin. So the allocator carries a persisted high-water mark: the maximum result ID ever allocated in the store's lifetime is tracked in memory and flushed into meta; boot resumes allocation above max(surviving rows, high-water mark). Unclean shutdown loses the mark — and wipes the store, minting a fresh UUID, which retires every old origin at once. The red test is pinned in T-S1: seed, export, prune the tail, clean-restart, execute new work, export — no origin pair may ever name two different results. A wiped store's old origins simply age out of the service (it is a cache).
  • Preserved through every hop. Import records the origin of every imported row; re-export emits it verbatim. A result created on engine A, imported by B, and re-exported in B's bundle still carries A's origin.
  • The dedup key, and nothing else. Import skips (or metadata-refreshes) rows whose origin is already present — the S2 idempotence. Origin never participates in lookup identity: recipe/content digests and terms do that, exactly as today. Two engines independently computing equivalent results have different origins and remain distinct rows related by digests — precisely R10's requirement.

Persistence shape: a new local table result_origins(result_id, origin_store_uuid, origin_result_id) (unique on the origin pair), populated at publication (locally-minted) and at bundle import (carried); flushed and restored like every mirror table; exported into every bundle. Locally-minted rows are stored explicitly rather than implied, so the invariant "every row has exactly one origin, ever" is checkable per-table (the T-S3 gate counts it). schema_version bumps (the sanctioned cost, reset lessons L6).

6.3  D2 — Cross-result references: one rewrite, at import

Rows reference other rows in four encodings today, and a foreign bundle's rows arrive speaking the exporter's ID space, so import must translate every one of them. This is the portable-ref contract: the complete inventory of where engine-local result IDs live in persisted bytes, each with its rewrite mechanism and a red test. Anything outside the inventory that turns out to hold a result ID is a contract violation fixed at the encode site, never papered over at import; and a row whose references cannot be made portable is excluded from the bundle with a typed counter (its in-bundle dependents then drop by the missing-dep rule at import) — degradation, never guessing.

The two rewrite mechanisms:

Frames — already structured, remapped by walk. A call frame's references are typed fields (ResultCallRef.ResultID — dagql/result_call_frame.go:64 — reachable via receiver, module, args, implicit inputs). Import walks each imported frame and rewrites every ref from bundle ID space to the local IDs assigned during this import. This walk is structured (it visits known fields, not JSON text) and must be: frame refs feed recipe-digest derivation (recipeDigestForCachedResult resolves through c.resultsByID), so they must point at live local rows before any identity is derived.

Payload envelopes — bare integers today, structured tokens after this phase. Object payloads and lazy fragments embed references as raw uint64 result IDs, all produced by one chokepoint — encodePersistedObjectRef (core/persisted_object.go:47) — and parsed back by type-specific decoders. The sites are numerous (git repos/refs, services, changesets, generators, module trees, and every registered lazy struct's ParentResultID/SourceResultID-style fields — e.g. persistedContainerWithRootFSLazy, core/container.go:702; 80+ encode calls across container/directory/file alone) but the bytes they produce are opaque to the persistence layer: nothing generic can find the refs to rewrite them. This phase changes the encoding at the chokepoint: encodePersistedObjectRef returns (and the persisted structs' fields and decoders carry) a ref token — a small type whose JSON form is {"$dagqlResultRef": N} — instead of a bare integer. The change is mechanical and compiler-enumerated (the type change surfaces every site); the persistence layer gains a generic, non-heuristic walk: any JSON object holding the reserved key is a ref; anything else is data. Import rewrites payload refs in the same pass as frame refs. schema_version bumps (same bump as D1's).

Two alternatives were considered and rejected — recorded because both will re-tempt:

AlternativeWhy rejected
Name-heuristic JSON walk (rewrite any field whose name looks like *resultID) — empirically functional in past use (provenance: §16). It is inference about intent from naming. A payload field that stores a number and happens to match the pattern gets silently corrupted; a ref field that doesn't match is silently missed until a warm run breaks. The reset design's ethos is explicit contracts at decision points, and the ref token is the same walk made contract-true at the cost of one sanctioned format bump.
Namespace-at-decode (never rewrite bytes; every row remembers which store's ID space its payload speaks; decode resolves refs through per-namespace origin maps). It trades one decision-point rewrite for a permanent, cross-cutting resolution concern: every decode path needs namespace context, per-store maps must be retained for as long as any undecoded payload speaking them exists, and the store stops having one ID space to reason about. Reset lesson L5's bias — the decision-point form, when clean, wins — applies squarely; the rewrite is clean.

The prune/import interaction, named honestly. Local prune and bundle import pull in opposite directions: an engine that prunes a row for disk pressure will see it return at the next boot if a selected bundle still carries it — churn, not growth (the row count is bounded by the selected bundles' contents; origin dedup caps it at one copy), and cheap churn at that (metadata only; content never re-fetches until demanded). The design accepts this for v1 and bounds it structurally: selection serves each store's newest bundle (§10 D3), so an engine's own pruning propagates through its next export — the fleet converges on retained state, and nothing keeps resurrecting rows that every engine has pruned. 7. Engine: export

The idea in three sentences. Export is the local flush pointed across the wire: the same in-memory snapshot pass local persistence runs at shutdown (snapshotPersistState, dagql/cache_persistence_worker.go:45 — graph lock held only for the copy-out) produces the rows, the bundle writer emits them in the §6 shape, and content chains are computed at that moment — never earlier (R4). The bundle's metadata publishes first and atomically; blob upload then streams as CAS-deduped delta, so interruption costs bytes, never correctness (S5/S6). Export runs when the engine is told to (a first-class admin API — in the cloud, the keeper calls it) or, opt-in, at graceful shutdown; it is decoupled from run success by construction (S4).

THE DECISIONS THIS SECTION MAKES
  1. Triggers: an authenticated engine admin API, plus an opt-in graceful-shutdown hook. The cloud lifecycle (keeper) drives the API and sequences export before instance teardown, so no platform grace window is ever a correctness deadline.
  2. Order: metadata publishes first, marked blobs_pending; blob upload follows (existence-checked delta, per-blob completion), then the completeness mark. Both interruption modes leave valid state.
  3. v1 policy: export the whole retained graph's metadata, and chains for every immutable snapshot it holds — with blob upload deduped against the CAS, so steady-state exports upload only what is new. A metadata-only mode is the recompute-forcing test lever. The policy hook is the seam for future cleverness.
  4. Chains are computed at export time on the existing layer-export machinery, with one pinned compression (zstd), and chain computation is cached per snapshot across exports.

7.1  D1 — Triggers, and who pulls them

The engine gains a small cache-service client, configured through engine config (service URL, auth token, cache scope, budgets, opt-in flags — absent config disables the whole feature). Two triggers:

  • The admin API (primary). POST /v1/cache/export on the engine's operator surface — a productized endpoint held to release compatibility, deliberately not one of the ad-hoc debug handlers (cmd/engine/debug.go), though it may share their listener. Exposure posture: the listener is operator/instance-internal (in the managed stack the keeper is a co-located sidecar), with an optional shared-secret header from engine config for defense in depth. The cloud depends on it. It snapshots and exports the current retained state. Concurrent calls coalesce onto the in-flight export (one export at a time per engine); the response reports the outcome summary (§11's counters). The caller in the managed cloud is the keeper — it already owns the "engine is idle ⇒ tear it down" decision, so the sequence becomes export (bounded) → teardown. Because the keeper waits, the platform's kill-grace window never truncates an export; and because bundles are valid when sparse (S5), even an operator-imposed budget just costs blobs.
  • Graceful shutdown (opt-in). With exportOnShutdown set, the engine exports inside GracefulStop after sessions drain and prune runs — the same steady state local flush sees (engine/server/server.go GracefulStop ordering) — bounded by a configured budget so shutdown cannot hang. This is the path for self-managed engines with no keeper. Metadata publishes early in the budget; blobs consume the rest.

Mid-serve exports are legal. The snapshot pass runs under the existing locks and does not require quiescence. One filter distinguishes it from shutdown flush: the export closure is the forward dependency closure of the persisted-edge roots — each root plus everything it transitively depends on, following sharedResult.deps downward, the same direction retention itself propagates. Rows outside that closure (retained only by live sessions) are another session's in-flight state, not durable cache, and are excluded. The exclusion cannot dangle a reference by construction: if a persisted root reaches a row through dependencies, that row is in the closure regardless of who else retains it — "session-only" rows are precisely the rows no persisted root reaches. Every projected table (results, deps, frames, envelopes, origins, chains, edges, and the identity rows for the closure's digests) is filtered to this same closure so the bundle is self-contained. At shutdown the closure and the whole store coincide (sessions are gone; the retained graph is the persisted closure).

7.2  D2 — Chains: content identity computed at the boundary

For every immutable snapshot link in the export closure, the exporter produces the chain: the ordered layer list, each layer a (diffID, blob digest, size, media type). The machinery exists — it is what container publish uses: per snapshot, walk its layer parents and obtain each layer's blob in the pinned compression, computing it if this snapshot has never been exported (ensureExportBlob, engine/snapshots/remote.go:63, and the compression-variant handling next to it). Three rules pin the behavior:

  • Hash-at-export only (R4). Nothing computes layer blobs or diffIDs during normal builds. First export of a snapshot pays the diff/compress cost; the resulting blobs and descriptors persist in the content store, so subsequent exports of the same snapshot are lookups. This makes export cost proportional to content new since the last export in the steady state — a measured quantity (§11), not an assumption either way.
  • One compression, pinned: zstd. The CAS dedups by blob digest; letting compression vary per engine silently halves dedup and surfaces as descriptor-variant conflicts wherever two engines' chains describe the same diff. Pinning removes the class outright; changing the pin later is a bundle-format version bump.
  • Mutable-owner snapshots produce no chain (§6.4): cache volumes, git/filesync mirrors cross as identity-only rows.

7.3  D3 — What to export: the v1 policy, and the seam

V1 exports, per trigger:

  • Metadata: everything retained. The full persisted-edge closure — every row, dep, identity table, origin. Metadata is the cheap, high-leverage half: it is what makes warm lookups hit at all, and its size (SQLite rows, no content) is megabytes at a typical retained-store scale of ~10⁴ results (evidence for the scale estimate: §16). Nothing is gained by curating it in v1.
  • Content: chains for every immutable snapshot in that closure. Not leaves-only: blob upload is deduped by digest against the CAS, and a leaf's chain already contains every ancestor layer, so offering all chains adds approximately zero bytes over leaves-only — what it adds is direct hydration for mid-chain results (a warm run that reads one intermediate directory pulls that chain, not a dependent's superset — R12's sparse story), and it removes a policy concept ("what is a leaf") from the correctness path entirely.
  • metadata-only mode (config/per-call flag): skip chains and blobs. Two consumers: the recompute-fallback proof (T-S5 forces the lazy-form path on a warm engine), and operators who want lookup-warmth without content storage.

The seam for future cleverness: the exporter consults one policy hook — selectExportContent(snapshot) → offer chain | skip — with exactly the two v1 implementations above (all-immutable, none). An analysis-guided policy (export only what history says gets reused) is a future implementation of this hook plus, symmetrically, the service-side selection seam (§10 D3). Nothing else in the pipeline changes when the policy does.

7.4  D4 — The export pipeline, end to end

  1. SNAPSHOT (existing machinery)
    Take the persist snapshot under the existing locks; filter to the persisted-edge closure. No new lock, no quiescence, no value-struct walking — rows come from materializationState exactly as local flush reads them (reset §8 D1).
  2. ENCODE
    Write metadata.db (mirror schema minus local-only tables, plus result_origins) and compute chains (D2) into manifest.json. Results whose chains fail to compute (e.g. snapshot pruned mid-export) degrade per-result: the row still exports with its lazy fragment; a row with neither is omitted from the bundle (never from the local store). Loud counter, never an export failure (S4).
  3. PUBLISH METADATA (atomic)
    POST /v1/scopes/{scope}/bundles with the archive. The service stores it and lists the bundle as blobs_pending. From this moment the export has durable value; everything after is enrichment.
  4. BLOB DELTA
    Batched existence check: POST /v1/blobs/stat with the manifest's blob index → the missing subset. Upload each missing blob (direct or presigned per backend, §10 D4), streamed from the content store. Per-blob failures retry, then skip — a skipped blob is sparseness, not failure (S5).
  5. COMPLETE
    POST …/bundles/{id}/complete with the uploaded/skipped tally → the bundle is marked blobs_complete (or stays pending with recorded gaps). The engine emits its export summary counters (§11) and, when triggered via the admin API, returns them to the caller.

Interruption analysis (the two halves of S6): die before step 3 — nothing published; any blobs previously in the CAS still amortize the next export. Die during step 4 — the bundle serves with sparser blobs; importers fall through per chain (S5); the next export from any engine re-offers the same digests and completes the gap. There is no state to repair in either case, which is the L8-dumbest possible failure handling.

8. Engine: bundle import at boot

The idea in three sentences. Boot gains one step, exactly where the reset design reserved it: after the local store restores, the engine downloads its selected bundles and merges each one through the same shape of pass local restore runs — per-result vetting, dependencies-first, drop-with-dependents — plus the two moves only foreign rows need: origin-keyed dedup against everything already present (S2) and reference rewriting into the local ID space (§6.3). A bundle that fails structurally is skipped whole and counted; it can never wipe or damage the local store (S4, L8). Everything after the merge is the reset design verbatim: imported rows are ordinary rows with sources, competing in lookup under R16-recomputed keys and the session-resource gate.

THE DECISIONS THIS SECTION MAKES
  1. Import order and atomicity: local store first, then bundles oldest→newest; each bundle merges all-or-nothing into memory; the whole phase runs under the boot lock (R14) within a configurable budget, degrading to fewer bundles / cold start (S4).
  2. Bundle failure semantics: store-level damage in a bundle ⇒ skip that bundle (never the local wipe); per-result damage ⇒ drop that result with its in-bundle dependents (the local vetting rules, bundle-scoped).
  3. Origin dedup is the row-creation gate, and skipped rows still join the reference remap so sibling rows rewrite correctly.
  4. Imported chains become materialization sources and persist locally (result_content_chains), so a warm engine's local restarts keep remote sources without re-downloading bundles.

8.1  The merge pass, per bundle

  1. FETCH + STRUCTURAL CHECK
    Download; verify manifest versions (bundle format, engine schema_version — a mismatch should have been filtered by selection; if present anyway, skip the bundle), open the metadata DB, read all tables. Any store-level failure — unreadable SQLite, broken identity-table references, zero IDs (the same named classes reset §8 D2 pins for the local store) — skips the whole bundle with a counted reason. The local import_failure wipe path is unreachable from bundle import, by mechanism, not assertion: the bundle reader is a separate entry point whose error type is "skip this bundle" — it shares the row-parsing and vetting helpers but is not called from importPersistedState, returns into the boot sequence after local restore has committed, and no branch of its error handling constructs CachePersistenceResetImportFailure or touches the local DB/worker reset paths (engine/server's reset loop consumes only local-restore errors). The red test is pinned in T-S11: a deliberately corrupted bundle imports as a skip, and the local store and worker state are bit-identical to a no-bundle boot.
  2. VET, DEPENDENCIES-FIRST (existing rules, bundle-flavored)
    The local vetting pass runs against the bundle's rows (dagql/cache_persistence_vetting.go): malformed rows drop; missing-dep and cycle rules apply within the bundle; drops cascade to in-bundle dependents. One substitution: the local "snapshots present in the worker store" check does not apply (bundles carry no refKeys); a bundle row's content viability is structural chain presence — availability of the chain's blobs is deliberately not checked at boot (S5; runtime fall-through owns that). Rows with no chain and no lazy fragment but a self-contained payload — scalars, mutable-owner identity rows — vet exactly as they do locally today: the as-built rule only drops a row whose claimed content is gone with no fallback (vetting.go:149–161), and an identity-only row claims none.
  3. ORIGIN DEDUP + ID ASSIGNMENT
    For each kept row, look up its origin pair in the store-wide origin index: present ⇒ no new row; record bundleID → existing localID in the remap table and refresh last-used metadata. Absent ⇒ allocate a fresh local ID, record the remap, stage the row. The remap table covers every kept row either way — sibling rows' references must resolve regardless of which side of the dedup their targets landed on. Same-origin observations union sources, never replace rows: when a later bundle carries a chain for an origin already present without one (the exporting store realized content after an earlier export), the existing row gains that content-chain source; nothing about an existing row is overwritten or removed by import — first-imported wins for row content, later observations may only add sources and refresh timestamps.
  4. REWRITE REFERENCES (§6.3, once)
    Frames by structured walk; envelope self-IDs (and per-item list IDs) structurally, since the persistence layer owns those fields; payload and lazy-fragment refs by the $dagqlResultRef token walk; persisted call IDs by the $dagqlCallID token (decode, rewrite handle-form, re-encode). A reference that misses the remap table (its target was dropped by vetting) drops the referring row with its dependents — the missing-dep rule, applied post-remap.
  5. MERGE IDENTITY + GRAPH
    Class digests teach into the live e-graph (ensureEqClassForDigestLocked / merge — this is where cross-engine equivalence composes); term keys recompute in the local space (R16, the same recompute local restore runs); deps and persisted edges land for staged rows (dedup on existing edges). Session-resource requirements recompute transitively, as local import already does.
  6. INSTALL SOURCES
    Each staged row's materializationState gets: a content-chain source per manifest chain entry (§9), and its lazy-form source when the envelope carries a fragment — ordered local snapshot → content chain → lazy form, per the source-order amendment this design proposes to the reset design (§9.1; an imported row simply has no first source until content arrives). Commit the staged bundle into the cache; move to the next bundle.

Ordering note: bundles merge oldest→newest (stable tie-break on bundle ID) so metadata refreshes deterministically favor the newest observation; row existence is order-independent by origin dedup. The whole phase is inside the R14 boot window — coarse lock, before serving, no new concurrency.

8.2  D3 — Retention and lifecycle of imported rows

Imported persisted edges become ordinary local persisted edges: what the exporter retained, the importer retains, and from that moment the local prune policy owns them — disk pressure prunes them exactly like local results (dagql/cache_prune.go's edge-cut model, unchanged). Imported rows flush to the local store at shutdown like any rows — carrying their origins and chains — so a warm engine that restarts locally is still warm without re-fetching bundles, and its own next export re-emits the imported rows under their original origins (the S2/S3 loop). There is no "imported" flag with behavioral meaning; provenance lives in the origin table and the counters, not in the serving path.

8.3  D4 — Budgets and degradation

The entire inflow — selection call, downloads, merges — runs within importBudget (config; default on the order of a minute). Budget exhaustion or any transport failure degrades monotonically: fewer bundles, else none — never a boot failure, never a partial bundle (per-bundle atomicity), never the local store's integrity (S4). Every degradation increments a typed counter and lands in the boot summary (§11): a cold start that should have been warm must be diagnosable from the engine's own logs.

9. Engine: the content-chain source

The idea in three sentences. The reset design reserved a third retained source — sourceContentChain, named in the fall-through order precisely so it would be designed exactly once (reset §7 D2, Fig. 4) — and this section makes it real. Realizing a content-chain source means: reuse whatever prefix of the chain already exists locally, fetch the missing layer blobs from the CAS, apply them as snapshot layers with the machinery image pulls already use, and hand the resulting local snapshot to the same decode path source ① uses — at which point the result also gains a local-snapshot source, so the chain is paid for once. Every failure semantic is inherited: a permanently missing blob marks the source non-viable, the walk falls through to the lazy form, and the floor is demote-to-miss (reset §9 D2/D3, unchanged).

THE DECISIONS THIS SECTION MAKES
  1. The chain source realizes into a local snapshot, then defers to the existing decode path — it is a content fetcher, not a second materialization model.
  2. Prefix reuse is mandatory, via the snapshot manager's imported-layer indexes — shared ancestry across results costs one copy.
  3. Failure typing: a 404 on a required blob marks this chain source non-viable for this boot; transport errors are transient (no marking; next waiter retries) — the reset design's marking rule applied to HTTP.
  4. Fetched content registers its identity once (snapshot-content links), so re-export of a hydrated result never re-hashes (R4's hash-once economy).

9.1  Where it plugs in — and the one amendment this design proposes

Reset §9 D2's realize() walks materializationState.sources in order inside the existing lazy singleflight (one runner, N waiters). This phase un-reserves the reserved enum value: an imported result's sources arrive from §8 as [content-chain, lazy-form] (no local snapshot yet); a hydrated or locally-built result's walk still finds its local snapshot first and never touches the network. The demand-boundedness is structural (R12): the walk runs for the one result being served, and a chain realizes only that result's snapshot — dependency inputs are touched only if the walk falls through to the lazy form, which recurses demand-driven exactly as designed.

PROPOSED AMENDMENT TO THE RESET DESIGN — RATIFICATION REQUIRED BEFORE CHUNK B

The reset design drew the fall-through order as local snapshot → lazy form → content-chain (reset §7 Fig. 4, and the enum-declaration order the source list sorts by, dagql/cache.go:1463–1520) — placing the then-reserved content-chain last. This design requires local snapshot → content-chain → lazy form: for a warm imported result, downloading its content is the mainline and re-executing its recipe is the fallback — the opposite order would make every warm engine re-run any work that has a persisted lazy form and reach for the network only when re-execution isn't possible, inverting the value proposition of remote cache (transfer is the point; recompute is the floor before demote). The counter-case is acknowledged: for some results a huge blob download can cost more than a trivial re-exec — that is per-result policy cleverness, explicitly out of v1 scope (§15); v1 takes the static order that matches the north star. The reset order was drawn while source ③ was a named placeholder with no consumer; this is the consumer. Process: this is a change to ratified reset text (Fig. 4 and the §7 D2 enum comment) — stop-and-discuss with the take-3 owner applies, and chunk B does not build until it is ratified there. Mechanically the change is the enum/sort order plus the Fig. 4 edit; no walk logic changes.

9.2  Realizing a chain

  1. PREFIX CHECK
    Walk the chain's layers in order, resolving the longest prefix that already exists locally via the snapshot manager's imported-layer indexes (imported_layer_blob_index/imported_layer_diff_index — the persisted maps from (parent snapshot, blob/diff digest) → local snapshot that exist for exactly this job). Two imported results sharing ancestry — the common case, since chains are layer paths through the same build graphs — share every prefix snapshot.
  2. FETCH MISSING BLOBS
    For each layer past the prefix: GET the blob from the CAS (direct or presigned, §10 D4) into the containerd content store. Concurrent fetches of the same digest across results dedup on the content store's ingestion locks — no new synchronization. Fetches run under the serving session's context with the client's budgets; this is the one serving-time network dependency the phase adds, and it is fall-through-protected (S4/S5).
  3. APPLY + REGISTER
    Apply the fetched layers on top of the prefix with the existing unpack/apply machinery (the image-pull path in engine/snapshots — pull.go / diffapply), extending the imported-layer indexes per layer. Register the final snapshot: refKeys + owner lease, and its snapshot-content links (chainID and blob digests — identity recorded at arrival, so a future export finds it memoized, §7 D2).
  4. HAND OFF
    The chain source writes the freshly-registered refKeys as the result's local-snapshot source and defers to the source walk, which now realizes source ① — the ordinary envelope-decode path — and marks the home realized (the sanctioned content-arrival write point, reset Fig. 2). Subsequent uses take the realized fast path; a later local restart restores this result with a real local snapshot.

10. The cache service (dagger.io)

The idea in three sentences. The service is three dumb stores and one small brain: a bundle inventory (Postgres rows + archives in object storage), a digest-addressed blob CAS (object storage), an append-only event log — and the selection function that answers a booting engine. It integrates with the managed-engine lifecycle at exactly two points: engines boot with cache-service configuration injected at provisioning (import needs no lifecycle command at all), and the keeper drives export before teardown through the engine's admin API. Its state is durable because it is boring — and disposable anyway, because it is a cache.

THE DECISIONS THIS SECTION MAKES
  1. API surface (D1): six engine-facing endpoints, org-token authenticated, versioned under /v1.
  2. Scope model (D2): cache namespace = (org, scope string); v1 scopes are operator-chosen (per repo by convention); no cross-org sharing.
  3. Selection (D3): newest bundle per distinct exporter store, up to K stores, matching the requester's versions, preferring blob-complete — one pure function of the inventory, and the service-side seam for future policy.
  4. Storage (D4): Postgres inventory + pluggable object storage (S3 and Namespace Artifacts as ported, battle-tested backends — §16; MinIO/filesystem for dev).
  5. Lifecycle (D5): config-injected import at provision; keeper-driven export before teardown over the salvaged command lane; export never gates run success (S4).
  6. GC (D6): retention by count/age per (scope, store), plus mark-sweep blob GC against live manifests — safe at any aggressiveness because of S5.

The wire mechanics are deliberately conventional and previously proven (multipart publish, stat-then-upload with alreadyExists short-circuit, presigned indirection — provenance: §16), while every server-side cache semantic is absent: there is no server-side "requested snapshots" decision, no merge on ingest, no import endpoint that composes state. Blobs are org-namespaced in storage layout but deduplicated within the org across scopes.

10.2  D2 — Scope and tenancy

A cache namespace is (org, scope): the org comes from the token; the scope string is engine configuration, by convention the repository identity for CI fleets. Everything — bundles, selection, insight — is per-namespace; blob bytes dedup org-wide (digest-addressed, org-prefixed). V1 makes no attempt at cross-org content sharing and no finer-than-scope access partitioning; within a scope, the session-resource gate (R7) and the salt partition (S10) remain the engine-side safety net they are locally. This is the deliberately-dumb v1 of tenancy; revisiting it (public base-content pools, per-branch scopes, salt strategy) is future work with its own security review.

10.3  D3 — Selection

Given a request (scope, schemaVersion, bundleFormat, limit K — engine default modest, e.g. 4): return the newest bundle per distinct exporter store UUID — the manifest's storeUUID, i.e. which store produced the bundle; deliberately not the per-row origin UUIDs, which live inside the metadata DB and would force the serving path to parse it (S7) — newest stores first, up to K, filtered to exactly matching versions, preferring blobs_complete over pending when both exist for a store. The semantic, stated precisely: the service mirrors each store's latest retained state. A store's newest bundle supersedes its older siblings including anything they contained that the store has since pruned — pruning deliberately propagates through export (§6.6's prune/import interaction depends on exactly this to stay churn-not-growth). Bundles from different stores are genuinely divergent state worth merging (M concurrent CI engines), which origin-dedup makes cheap to combine. A selection that instead unioned a store's bundle history would retain more — and would also resurrect every pruned row forever; v1 chooses the converging semantic, and richer selection is shelved (§15). This function is the service's entire intelligence, it is pure over the inventory, and it is the service-side seam: a future policy (workload-aware selection, bundle slicing) replaces this function without touching storage, protocol, or engine.

10.5  D5 — Lifecycle of managed engines

  • Import needs no command. Provisioning injects cache-service configuration (URL, org token, scope, budgets) into the engine's environment; the engine imports at boot by itself (§8). A command-driven import path would also need queue-fairness rules so boot-critical imports never starve behind queued exports; config-driven boot import removes that class outright — an engine that imports at boot cannot be starved by anything on a command lane.
  • Export is keeper-driven. The salvaged command lane (engine_cache_commands, schema 00097: queued/claimed/completed with idempotency keys and provider-instance matching) carries one command kind: export. The check runner enqueues export-after-green; the keeper also triggers export in its idle-teardown sequence (export → then teardown), so shutdown grace windows never truncate exports (§7 D1). The keeper claims, calls the engine's admin API, records the outcome. Export commands are best-effort: failure marks the command failed and the event logged — never the check (S4).
  • Self-managed engines use the same engine features with no keeper: config + exportOnShutdown, or explicit admin-API calls from their own automation.

10.6  D6 — Garbage collection

Two independent, boring collectors: bundles — keep the newest N per (scope, store UUID) and drop bundles older than a max age or superseded beyond N (inventory row + archive deleted together); blobs — periodic mark-sweep: the live set is the union of live bundles' manifest blob indexes; unreferenced blobs older than a safety window are deleted. Any aggressiveness is safe: an over-eager sweep only creates sparseness, which the engine already survives per-chain (S5). GC actions land in the event log and the inventory surfaces (§11).

11. Observability and insight

The idea in three sentences. Two audiences, one discipline. For proofs and debugging: engine counters extending the reset design's outcome vocabulary across the wire, every one consumed by a named gate case (R8/S8 — nothing decorative). For understanding — "I need visualizations, I need to understand the cache, the state of it" — the service carries a read-only insight layer over its inventory, event log, and (best-effort, version-aware) bundle contents, surfaced as JSON endpoints plus a small dashboard.

11.2  Service insight (the understanding surface)

  • Inventory API: per scope — bundle timeline (store, age, status, counts), blob store totals, coverage (fraction of manifest blobs present per bundle — computable from stat), GC activity. Pure Postgres queries.
  • Event log API: filterable publish/select/complete/GC events — "which engine exported what, when; who imported it" as one query. This is the operational debugging spine: its consumer is an operator answering a lifecycle question as one query instead of reconstructing it from scattered logs.
  • The indexer (read-only, version-aware, best-effort — §2's boundary): parses manifests always (they are service-versioned), and metadata DBs for known engine schema versions, materializing per-bundle facts: result counts by type, origin-store composition, chain/blob statistics, overlap between bundles (shared origins). Unknown versions degrade to manifest-only. Indexer output feeds the dashboard; nothing on the serving path reads it.
  • The dashboard: one server-rendered page per scope — bundle timeline, growth curves (rows and bytes over time: S3's measurement made visible), blob coverage and dedup ratio, recent events, and the engine-side stats files' warm/cold summaries when uploaded alongside CI runs. V1 is deliberately plain (tables + inline SVG sparklines); it exists so that "what is the state of the cache" is a page, not an investigation.

11.3  Reconciliation note

All of this is process/ops tooling in the reset design's sense (§5 there): built properly, scoped to this effort, expected to reconcile with the parallel OTel-based observability workstreams (engine telemetry, cache-perf analysis) rather than outlive them as-is — and deliberately not entangled with them now. The one intentional overlap: engine export/import operations emit ordinary spans so cloud traces show cache lifecycle cost alongside build cost.

12. The dev stack and the test ladder

The idea in three sentences. Every rung below the last runs with zero external credentials (S9): the engine side proves itself in-repo against a protocol-faithful test service; the real service proves itself in dagger.io against containerized Postgres/MinIO and real dev engines, all inside Dagger. One conformance suite — protocol-level tests parameterized over an endpoint — runs against both the test service and the real one, so the two cannot drift silently. The only credential-gated step is the final live deployment, and by the time it runs, everything it exercises has already passed twice.

12.1  The ladder

  1. DAGQL UNIT (dagger/dagger)
    Bundle round-trip against in-memory/file stores: encode a seeded store → import into a fresh store → identical key derivation and hit behavior (T-S1, the bundle analog of the reset's renumbered-store T5); origin dedup (T-S2 red test); the ref-token walk (loud on unknown shapes); bundle-flavored vetting matrix. The bundle reader/writer is factored over plain streams, so this rung needs no network at all.
  2. IN-REPO INTEGRATION (dagger/dagger)
    The persistence suite's dagger-in-dagger pattern, extended: two dev engines with different state keys plus the in-repo test service — a small Go binary (internal/testutil/cacheservice) implementing the /v1 protocol over filesystem storage, doubling as the protocol's reference implementation — wired as Dagger services exactly like the restart tests wire engines today (core/integration/engine_persistence_test.go's start/stop helpers). Secret-salt pre-seeding (<rootDir>/secret-salt, 32 bytes) is a harness helper so cross-engine tests share handle identity deliberately (S10). This rung carries T-S3 through T-S8 and the conformance suite. It is R11's requirement made real: the full remote model provable in dagger/dagger with no cloud stack.
  3. SERVICE HARNESS (dagger.io, no dev stack)
    api/cmd/cacheservice-dev-server: the real route registration + real handlers against MinIO and either embedded or containerized Postgres — the cheap-loop-before-full-stack gate: real handlers and real storage at a fraction of a full-stack cycle's cost, so protocol drift surfaces here rather than in the expensive rungs (provenance of the pattern: §16). Runs the conformance suite against the real handlers, plus real-engine round-trips (engine binaries in containers ↔ dev server ↔ MinIO). Zero credentials.
  4. E2E (dagger.io, full stack)
    The full stack stood up inside Dagger, in the same style as dagger/dagger's own integration suite — every needed service containerized and wired in-test: API server with the cache-service handlers, Postgres, MinIO, keeper, two or more dev engines. Exercises the lifecycle end to end — provisioning-style config injection, a simulated green check enqueuing export, keeper claim → engine admin API → bundle published, teardown sequencing, fresh engine imports and runs warm — plus the growth gate (T-S3) and GC safety (delete unreferenced blobs; live runs unaffected). Still zero credentials.
  5. LIVE (credential-gated, the only such step)
    Deploy to the managed dev stack (Namespace providers, the real keeper wiring, the real tenancy). Run the cloud warm proof (§13). This rung reuses the existing operational runbooks — the fresh-engine destroy-and-reconcile discipline, the PR-trigger harness — as procedure, not as code (§16). It is designed to be executed by whoever holds credentials, on top of artifacts that are already fully proven below; agents without credentials stop at rung 4 with nothing left unproven but the deployment itself.

12.2  Namespace awareness without Namespace access

Three concrete design choices keep rung 5 thin: the engine consumes only environment configuration (anything that can inject env vars can provision cache-enabled engines — Namespace, helm, docker run); the service's Namespace-specific surface is one blob-store backend (ported, already battle-tested) plus the keeper it already ships; and the export trigger is an ordinary authenticated API call, so keeper integration is invocation, not protocol. The live rung validates wiring and tenancy, not mechanisms.

13. The warm proof: definition of done

The idea in three sentences. The phase is done when a fresh engine, booting against the service, provably serves another engine's work — outputs equal on a random-marker pipeline and counters that would have failed loudly on silent recompute — with growth flat across ≥3 cycles, idempotence proven by red test, and every degradation path (sparse blobs, metadata-only, salt partition) exercised and counted. Done is demonstrated three times: in-repo, in the dagger.io e2e, and live on cloud engines.

13.2  The acceptance bar

  1. IN-REPO
    Three consecutive fully-green runs of the complete in-repo gate (Step-0 + T-S1…T-S9's in-repo rungs), stats files attached as evidence — green with evidence, not by exit code.
  2. DAGGER.IO E2E
    The full-stack suite (rungs 3–4) green with the same evidence discipline, including T-S3's multi-cycle growth record and T-S10.
  3. LIVE
    One complete cloud warm proof on the managed dev stack: cold seed from a real CI-shaped run on one engine; engines destroyed with the fresh-engine discipline; a warm run on freshly-provisioned engines — outputs equal, counters attached, service event log corroborating (export → selection → fetches). Two properties are explicitly pinned into this proof because they are the easiest to quietly skip (why they are called out: §16): the proof must hold across a service restart between seed and warm run — exercising the durability §2 claims — and the run records a wall-clock cold-vs-warm comparison on the same pipeline, reported honestly as measurement rather than a pass/fail bar, so the speed claim is evidenced, never assumed.
  4. DONE MEANS
    All of the above, this document updated to as-built through the review process, and the shelf re-examined once. Then the deferred cleverness (analysis-guided policy, selection intelligence) can start as its own effort against the two named seams.

  1. A — Bundle & origins (dagql, no network). Origin minting/persistence, the ref token, the bundle writer/reader over streams, bundle-flavored vetting, origin dedup. Gate: T-S1, T-S2 + Step-0.   2. B — Chains & the content-chain source (engine). Depends on reset §9's source walk being landed (it is the direct substrate) and on the §9.1 source-order amendment being ratified in the reset design — chunk B does not build before that ruling.
  3. C — Transport & the in-repo service. The service client, the test service, the admin API + shutdown hook, the conformance suite, the full in-repo integration suite. Gate: T-S3, T-S5, T-S7, T-S9 (rung 2) + Step-0.
  4. D — The real service (dagger.io). Handlers, storage backends (ports), migrations, dev server. Gate: conformance (rung 3) + backend unit suites (S3/MinIO verification semantics).
  5. E — Lifecycle. Keeper export command, checks enqueue, provisioning config, e2e full-stack suite. Gate: T-S9 (rung 4), T-S10, e2e warm proof + growth gate.

15. The shelf (not part of the design)
What the shelf is. Deliberately set aside, not pre-decided. Unshelve only against a real need, with review.
  • Bounded semantic row dedup (collapsing distinct-origin rows with identical recipe digests + output classes at import, bounded per class). The e-graph already serves across equivalents; this is a metadata-size optimization with real subtlety (multiple materializations per class are a feature). Unshelve if T-S3-scale measurement shows independent-equivalent accumulation actually costing something.
  • Delta / sliced bundles. Whole-snapshot bundles are the v1 simplicity anchor; selection-side slicing or exporter-side deltas are pure optimizations once measurement demands them (S6 note: metadata size is a measured surface).
  • Smarter selection / analysis-guided policy. The two named seams (§7 D3, §10 D3). Explicitly the next phase's territory, not this one's. Includes richer per-store selection (unioning a store's bundle history) and its prerequisite machinery — prune tombstones / cross-engine retention consensus — which v1's converging newest-per-store semantic deliberately avoids (§6.6, §10 D3).
  • Salt unification / finer tenancy. S10's tracked deferral; needs its own security-reviewed design (cloud-managed salt distribution, or handle schemes that don't partition).
  • Import command lane / mid-serve import. Deleted in this design (boot import is config-driven; R14 stands). Would return only with a quiesce design per the reset non-goals.
  • Open protocol commitments. The protocol is versioned and the test service is a reference implementation, but publishing it as a stable third-party contract is a product decision for later.
  • Engine-to-engine / file-share transport as a product feature. The bundle reader/writer is stream-factored and the unit rung uses files, so "export to a directory" nearly exists; productizing it (NFS-shared caches without a service) is deliberately not v1 surface.
