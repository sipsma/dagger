Remote Cache — The Cache Manager

v1 draft  ·  successor to the superseded store-and-select design  ·  2026-07-07

Status. Draft for adversarial review. This document supersedes ../service/design.html (retained as the review-log record of the rejected architecture and of the landed engine work). It is written against the owner's architecture guidance of 2026-07-07, which is binding throughout, and against the salvage maps produced at the pause: the engine map (take-3 worktree SALVAGE-MAP-ENGINE.md) and the chunk C/D/F STATE-OF-WORK.md files. The reset design (../reset/design.html) and lessons L1–L8 remain fully binding; engine chunks A+B are landed reality (integration tip 07e050e233, schema 19) and this design consumes them as built.

1. The goal

The cache service is a cache manager: the component that holds the cache semantics of the fleet. It maintains one merged view of the cache across all engines in a scope — every result, every equivalence, every content chain, from everyone — and it makes the intelligent decisions that only that view makes possible: what is worth uploading, what should be cached and whether it is, what to prune and when. Engines remain the executors and the local caches; the manager is where fleet-level cache intelligence lives, and "smart" is a fundamental product feature, not an optimization to defer.

The concrete v1 loop:

  • An engine finishing work tells the manager what it has (metadata + content manifests — no bytes). The manager merges that knowledge into the merged view and answers with exactly which records' content it wants uploaded; the engine uploads those blobs and nothing else. The upload decision lives server-side.
  • A booting engine downloads its scope's merged artifact — the composed, deduplicated state of everyone's cache — and imports it through the exact machinery it already uses (landed chunks A+B), as the single-artifact case of what it already does. Content still moves lazily, by digest, on demand.
  • The manager's view is durable (service restarts lose nothing), idempotent under ingest (origin identity — landed — makes re-announcement a no-op), and pruned server-side with the engine's own prune machinery.

The proof is unchanged in spirit from every prior take: a cold run on one engine seeds the manager; a warm run on a fresh engine hits, with counters that would have failed loudly if reuse hadn't happened — plus the new, manager-specific proofs: N engines' work visible as one merged view, ingest idempotence measured server-side, and the upload decision demonstrably server-made.

Deliberately deferred (the seams exist; the cleverness comes later): the analysis-driven upload policy (§10 names the wcprof convergence seam explicitly — v1 policy is simple); server-only re-layering of the imported engine code; backwards compatibility across engine/service versions (§12 — alignment is assumed, by ruling).

2. The load-bearing structural decision

The merged view is the product, and it is held by the engine's own cache code running server-side. The manager embeds the engine's cache implementation — the e-graph, the persistence store, the bundle ingest/compose machinery, the prune engine — imported as a Go module from the open-source repo, and maintains one durable, per-scope cache store that every engine's exports merge into. Nothing about cache semantics is reimplemented, approximated, or mirrored: the code that decides equivalence on an engine decides it in the manager, because it is the same code. What the manager adds is what only a fleet-level component can add — the merged view itself, the upload decision, retention policy over everyone's cache, and the insight surfaces.

Two named couplings stay dead, one from each prior failure:

  • Opaque bundles / store-and-select (the superseded design): a service that stores exporter bundles as sealed units and only chooses which to hand back can never make an intelligent decision about a record — not what to request for upload, not what to prune, not what is worth caching — because it cannot see records at all. Every future capability of this product runs through record-level visibility; opacity caps the product at "a bucket with a listing," and that ceiling is not acceptable. Any proposal that reintroduces a semantics-blind serving path for metadata is this coupling returning (content blobs are the deliberate exception: they are opaque bytes by nature, addressed by digest — §7).
  • The fragile merge (the v2-era failure shape): a server-side merge whose state is process memory (every restart loses the fleet's accumulated cache and forces a re-seed), and whose ingest mints fresh row identity per arrival (import → re-export cycles compound rows without bound). Both defects were properties of that implementation, not of server-side merging — and both are now structurally closed by machinery that has landed: the merged store is a durable persistence store with the engine's own restore/flush lifecycle (§6), and ingest deduplicates by origin identity, the mint-exactly-once row identity that chunk A built and that protects any importer, engine or manager alike (§7). The pivotal inversion of the salvage: origin identity was built to protect engines merging bundles; its greatest value lands server-side, protecting the merged view.

Why importing the engine code is the implementation and not a shortcut: the merge is the hard part of this product, and the engine already implements it — equivalence classes with congruence, origin-idempotent arrival, per-result vetting with honest blast radii, reference rewriting, portable encoding, restore-deterministic keys, pruning with retention roots. Every one of those was designed, adversarially reviewed, and landed in the open-source engine within this program. Rewriting them server-side would be the ridiculous option; the previous era's server merge already validated that the engine's cache embeds and runs server-side (the failure was its statelessness and identitylessness, both since solved — above). Version alignment between the imported module and the fleet is assumed by ruling (§12), which is exactly what makes this clean: the manager is another consumer of the same code at the same version, not a protocol peer across a compatibility chasm. Layering the engine code so server-only concerns separate more cleanly is future work by ruling, not v1.

3. Requirements and non-goals

Normative. M-numbers are this design's requirements. Carried requirements from the engine fundamentals (R1–R16, reset design) remain in force for the engine side; carried S-requirements from the superseded design are renumbered here where they survive, and their dispositions are recorded in §4 round 0. Notably: old S7 (engine-schema-agnostic service) is retired by owner ruling — see M8.

M1 — One merged view per scope, record-visible

The manager sees every record from every engine as one cache — never sealed units it can't look inside.

The manager maintains, per cache scope, one merged cache store containing every ingested result row, identity table, and content-chain reference from every engine in the scope, held in the engine's own cache representation via the imported engine module. Every manager decision (upload, prune, insight) operates on records in this view. No serving or decision path treats engine-produced metadata as opaque. Content blobs are the deliberate exception: bytes are opaque, addressed by digest, stored in the CAS.

M2 — The merged view is durable

A manager restart loses nothing. The fleet's accumulated cache is state, not cache-of-a-cache.

The merged view survives service restarts and redeploys without re-seeding from engines: it is persisted with the engine's own persistence machinery and checkpointed to durable storage (§6). Losing it is a disaster-recovery event with a defined, honest recovery (engines re-announce over time; the view rebuilds), never a routine consequence of operations. In-memory-only merged state is forbidden.

M3 — Origin-idempotent ingest (was S2, re-homed server-side)

Announcing the same work twice — or from two engines that both imported it — adds zero rows to the merged view, ever.

Ingest deduplicates by the landed origin identity (chunk A): a row whose origin pair is already in the merged view is never re-created; identity evidence unions; re-announce is a no-op. The red test runs server-side from day one: ingest the same announcement twice ⇒ zero merged-view growth. The growth gate (≥3 cycles across multiple engines, flat modulo new work — was S3) is measured on the merged view.

M4 — The upload decision is the manager's

Engines propose; the manager disposes. What content gets uploaded is decided against the merged view, server-side.

The export protocol is negotiate-then-upload: the engine announces metadata + content manifests; the manager answers with the exact set of blobs it wants; the engine uploads those. The decision function is a named, server-side policy hook over (the merged view, the CAS inventory, the announcement) — v1 policy is deliberately simple (§10), and the hook is the explicit convergence seam for the cache-performance analysis workstream (wcprof what-if-cached): the long-standing intent is that analysis output decides what is worth caching. Engines never self-decide uploads beyond what the manager requested.

M5 — Cache traffic never breaks builds (was S4) + sparse safety (was S5)

Everything about the manager is an accelerator; blob availability is never a correctness input.

Announce/upload failure never fails a green run; boot-import failure or timeout degrades to cold start under a budget; blob-fetch failure at serving time falls through the landed source walk to the demote floor. Metadata may reference content the CAS no longer has, and nothing breaks — which is what makes manager-side blob pruning safe at any aggressiveness. Every degradation is loudly counted.

M6 — Falsifiable observability (was S8), now including manager semantics

Every merge, decision, and serve is countable; the proofs consume the counters.

Engine counters carry over as landed. The manager adds its own: per-ingest {rows_offered, rows_new, rows_deduped_by_origin, blobs_requested, blobs_declined}, per-compose {rows, chains, generation}, prune outcomes, CAS sweep tallies — each consumed by a named gate case or insight surface. Proof-of-reuse remains by consequence (random-marker equality) plus counters.

M7 — Credential-free development to the last step (was S9)

The full manager loop runs and proves itself with no external credentials.

The manager core is buildable and testable in-repo (§13): the merge, negotiate, compose, and prune loops run against filesystem storage in dagger/dagger integration tests; the dagger.io shell adds tenancy, Postgres, real CAS backends, and deployment. The only credential-gated step remains the live cloud deployment.

M8 — Version alignment assumed; compatibility out of scope

Engines and the manager run aligned versions. Mismatch is rejected loudly, never bridged.

By owner ruling, backwards compatibility is explicitly out of scope for this design: the fleet and the manager are assumed version-aligned (same engine module version, same persistence schema, same wire shapes). The manager asserts alignment per request and rejects mismatches with a typed error; a manager upgrade that changes the persistence schema wipes its merged stores (the sanctioned wipe-on-upgrade rule) and the view rebuilds from re-announcements. No migration code, no version bridging, no schema-agnosticism — the superseded design's S7 is retired, and designs must not be shaped by redeploy avoidance.

M9 — Session-resource soundness crosses intact (was S10)

Handle-form only, in the merged view as everywhere; the salt partition is visible and narrower than once thought.

The merged view carries session-resource dependencies in handle form only (guaranteed by the persisted encoding). As-built refinement carried from the pause: only URI-form secret handles and SSH-fingerprint handles are salted (per-engine partition); setSecret handles are salt-independent and portable. The partition surfaces at identity level (a different-salt engine simply has no candidates), and the typed eligibility counter exists for the same-engine shapes it can observe.

Explicit non-goals (v1) NON-GOALS

  • Opaque metadata anywhere in the manager. The rejected coupling (§2). Content blobs in the CAS are the sole sanctioned opacity.
  • Analysis-driven upload/retention policy. The hook is v1 (§10); the analysis consumer is the named next phase.
  • Backwards/forwards version compatibility. M8. Future "annoying boilerplate," by ruling — not fear, sequencing.
  • Server-only re-layering of the engine cache code. Import it whole; factor later if real needs emerge.
  • Cross-scope/cross-org content sharing, finer tenancy, salt unification. Carried deferrals.
  • Mid-serving engine import (R14 stands), continuous engine↔manager sync. Engines import at boot and announce at export points; anything streamier is future.

5. Target shape

Cross-section invariants

  • Cache semantics run in exactly one codebase — the engine's, imported (M1, §2). The manager holds no second identity model.
  • Per scope, the merged view has one writer at a time; every mutation lands durably (flush + checkpoint) before its effects are served (M2, §6).
  • Ingest is origin-idempotent; re-announcement and overlap are no-ops by construction (M3, §7).
  • Metadata is record-visible everywhere in the manager; the CAS is the sole opaque layer (M1); blob availability is never a correctness input (M5).
  • Version alignment is asserted, never bridged (M8, §12).

6. The merged view

The idea in three sentences. A scope's merged view is an engine cache store with no engine around it: the same e-graph, the same SQLite persistence file (schema 19), the same restore/flush lifecycle, owned by the manager process through the imported engine module — constructed exactly the way the v2-era server merge already proved viable (dagql.NewCache with no worker/snapshotter), but with the two fatal omissions of that era corrected: it has a real DB path (the engine's own persistence machinery makes it durable), and every arrival is origin-deduplicated (the landed chunk A machinery). Durability beyond the local disk is a generation-tagged checkpoint of the SQLite file in object storage, with a Postgres scope registry and a single-writer lease serializing all mutation per scope.

THE DECISIONS THIS SECTION MAKES
  1. Physical form: one engine persistence store (SQLite, schema 19) per (org, scope), operated by the imported engine cache code with a nil worker/snapshotter — the mode the landed code already supports.
  2. Durability: local store + per-generation checkpoint to object storage; a Postgres scope registry {org, scope, generation, checkpoint key, schema_version}; recovery = restore latest checkpoint, and the disaster floor is re-announcement (M2).
  3. Concurrency: one writer per scope (Postgres advisory lease — the converged chunk D pattern), mutations serialized; reads serve from composed artifacts, not the live store.
  4. Identity: the merged store has its own store UUID + allocator high-water (landed machinery, verbatim); ingested rows keep their engine origins verbatim, which is what makes the entire downstream (engine re-import, re-announce, multi-manager futures) idempotent.
  5. Memory: scope stores activate on demand and close when idle (flush → checkpoint → close); the manager holds a bounded working set of live scopes.

6.1  What the manager actually runs

The manager-core uses exactly four engine entry points, all landed:

OperationEngine entry point (as landed)Manager use
Open / restore a scope storedagql.NewCache(ctx, dbPath, nil, nil) — restores persisted state, rebuilds the e-graph with R16-recomputed keys, per-result vetting; nil snapshot-manager operation is supported (lease attachment and content checks skip when nil — verified in the landed vetting/import paths, and validated in practice by the v2-era server merge) Scope activation: fetch latest checkpoint → open → serve the loop

Engine-side deltas this requires (small, version-aligned, sanctioned): (1) a public flush entry point (Cache.Flush(ctx) wrapping the existing persistence worker's flush) so an embedder can persist without closing — today flush happens at Close; (2) compose must re-emit stored chains (result_content_chains) for rows that arrived with chains, since the manager has no snapshotter to compute any — the landed export reuses memoized/stored chains and never computes without a snapshot manager, but this exact nil-snapshotter compose path is the one seam to verify at implementation, pinned as a red test (a store with imported chains and nil snapshotter exports those chains byte-identically); a failure here is stop-and-discuss, not a workaround.

6.2  Durability: flush, checkpoint, generation

  1. MUTATE (under the scope lease)
    An ingest (or prune) mutates the live store through the engine code.
  2. FLUSH
    Flush writes the store's SQLite snapshot — the engine's own whole-snapshot-rewrite persistence, clean-shutdown markers included.
  3. CHECKPOINT
    The SQLite file uploads to object storage under a fresh generation key; the scope registry row updates {generation, checkpoint key} transactionally. Only after this commit are the mutation's effects eligible to serve (artifact composition reads generations, §8).
  4. CRASH ANALYSIS
    Crash before checkpoint-commit ⇒ the registry still points at the previous generation; the local file is discarded on next activation (its markers may be unclean — the engine's own wipe-on-unclean rule applies to the local copy, and recovery is simply the previous checkpoint). The lost announcement re-arrives on the announcing engine's next export and merges idempotently (M3). Nothing needs repair — L8's dumbest treatment, inherited.

v1 checkpoints after every mutation batch (one announcement = one batch). Checkpoint upload cost is bounded by store size; batching/incremental checkpointing is shelved until measurement demands it (M6 counts flush/checkpoint durations per scope).

6.3  The scope registry and the lease

-- Postgres (the manager shell); the merged stores themselves are engine SQLite files
CREATE TABLE cache_scopes (
    org_id          UUID NOT NULL,
    scope           TEXT NOT NULL,
    generation      BIGINT NOT NULL DEFAULT 0,
    checkpoint_key  TEXT,            -- object-storage key of the current SQLite checkpoint
    schema_version  TEXT NOT NULL,   -- the engine persistence schema this store speaks (M8)
    updated_at      TIMESTAMPTZ NOT NULL,
    PRIMARY KEY (org_id, scope)
);

All mutation for a scope runs under a Postgres advisory lease keyed (org, scope) — the converged chunk D locking pattern, re-homed: replica-safe single-writer, held for the mutate→flush→checkpoint window. Readers never take it (they read composed artifacts and registry rows). Idle scope stores close after a TTL (flush → checkpoint → close); an activation on another replica simply restores the latest checkpoint. Announcement ordering across engines is whatever the lease serializes — order does not matter, because ingest is commutative up to origin-dedup and identity teaching (the e-graph's merge is order-independent for equivalence facts).

7. Ingest: negotiate, then upload

The idea in three sentences. An engine's export becomes a conversation: it sends the manager its metadata — the same portable encoding it persists locally, with chain manifests describing what content exists, and zero content bytes — and the manager, having merged that knowledge into the view, answers with exactly the blobs it wants uploaded (presigned targets included). The engine uploads those and completes; the CAS machinery is the converged chunk D pipeline unchanged (staging + promote, verified inventory, completion authority). The decision of what to request is a server-side policy over the merged view (§10) — which is the entire point: the manager can decline content it already has from anyone, content it deems worthless, or content policy says to skip, and the engine never wastes the bytes.

THE DECISIONS THIS SECTION MAKES
  1. The announcement payload is the existing bundle encoding (manifest + metadata.db, blob-less) — the landed engine export pipeline survives with its trigger semantics (admin API + shutdown hook) and its two-phase shape re-pointed: publish → the negotiate response replaces blind stat-then-upload-everything.
  2. The merge happens at announce time, before the upload answer — so the answer is computed against the post-merge view (a second engine announcing the same content gets "nothing, thanks").
  3. One announcement = one validation unit (whole-announcement skip on section garbage; per-row damage drops rows with in-announcement dependents) — the landed ingest semantics at exactly the right blast radius.
  4. The wire protocol is minimal: announce → {requested[], upload targets, complete} → uploads → complete. The v2-era RequestedBlobs response is the validated ancestor; chunk D's stat/uploads/complete endpoints survive beneath it.

7.1  The protocol

// All under org-token auth; version headers asserted per M8/§12.

POST /v1/scopes/{scope}/announce          // multipart: manifest + metadata.db (blob-less bundle)
  → {
      "generation":  N,                   // merged-view generation after this ingest
      "ingest":      { "rowsOffered": …, "rowsNew": …, "rowsDedupedByOrigin": …,
                       "skipped": bool, "skipReason": "…" },      // M6 counters, echoed
      "requested":   [ "sha256:…", … ],   // the manager's upload decision (§10)
      "declined":    M,                   // count of offered-but-not-requested (typed in events)
      "uploads":     { … }                // chunk D's prepare/complete flow for the requested set
    }
POST /v1/blobs/uploads, /v1/blobs/uploads/complete, GET /v1/blobs/{digest}
                                          // UNCHANGED — the converged chunk D CAS surface
GET  /v1/scopes/{scope}/artifact          // §8 — replaces the retired selection endpoint

The engine-side pipeline is chunk C's parked shape with the negotiation folded in: encode (blob-less bundle) → announce → upload exactly the requested set (the existing budget-bounded, retry-then-skip uploader) → complete. Interruption analysis is unchanged from the landed two-phase design: metadata always lands first (the merge happened), an interrupted upload just leaves the CAS sparser, and sparseness is legal everywhere (M5). The trigger surfaces (operator endpoint + exportOnShutdown in GracefulStop, coalescing, summaries) survive as parked.

7.2  Server-side sequence, per announcement

  1. ASSERT ALIGNMENT (M8)
    Engine version / persistence schema headers must equal the manager's own; mismatch ⇒ typed 409, counted, never bridged.
  2. LEASE + INGEST
    Take the scope lease; ImportBundle the announcement into the merged store. Skip-typed failure ⇒ the announcement is rejected as a unit (typed response + event); the merged view is untouched (the landed all-or-nothing commit).
  3. DECIDE (§10)
    requestedBlobs(view, casInventory, manifest) — v1: every chain blob in the announcement's blob index not verified-present in the CAS. Declines are counted and event-logged with the policy's reason vocabulary.
  4. FLUSH + CHECKPOINT + RESPOND
    §6.2's durability steps; the response carries the new generation, the ingest counters, and the requested set with upload targets. Blob uploads then proceed against the CAS exactly as converged (verification, promotion, inventory).

Ingest work is metadata-scale (the landed engine-side merge measured ~4600 rows in low seconds inside the boot window; the manager pays the same shape plus flush + checkpoint I/O — M6 measures it per scope). Announce is synchronous end-to-end in v1: simplest, and the engine's export path is already budget-bounded and failure-tolerant around it.

8. Serving engines: the merged artifact

The idea in three sentences. What a booting engine downloads is an ExportBundle of the merged store: the forward closure of the merged view's retention roots, in the one portable encoding, with the merged store's UUID as the composer identity and every row's engine origins preserved verbatim inside. The engine imports it through the landed machinery as the single-unit case of what it already does — no engine changes beyond deleting the multi-bundle selection loop (which was the store-and-select residue chunk C's salvage map already isolated). Composition is lazy and generation-cached: the first artifact request after a generation bump composes and stores the artifact; every other request until the next bump is a redirect.

THE DECISIONS THIS SECTION MAKES
  1. The artifact = server-side ExportBundle of the merged store, whole-scope in v1, generation-cached in object storage; composed under the scope lease, served without it.
  2. Engine boot import goes K=1: fetch the scope artifact, import it, done. The multi-bundle loop, selection call, and their counter shapes retire (chunk C parked resume note); the boot budget, monotone degradation, and boot summary survive.
  3. Artifact integrity keeps the landed semantics: an engine that receives a damaged artifact skips it whole and boots cold (honest, M5); the manager treats a failed composition as a bug surfaced by its own compose-time validation, regenerates on demand, and never serves a partial write (compose → verify → publish-by-rename).
  4. Origins inside the artifact are the engines'; the manifest's composer UUID is the merged store's — the salvage map's "manifest StoreUUID connotation" fix lands here: the field means "who composed this unit," and nothing keys on it (verified in the landed code).

8.1  Composition and caching

  1. REQUEST
    GET /v1/scopes/{scope}/artifact (version headers asserted, M8). The registry row gives {generation, artifact key?}. Cached artifact for this generation ⇒ 307 to it.
  2. COMPOSE (lease held)
    Activate the scope store (restore checkpoint if cold), ExportBundle the forward closure of its persisted roots to a staging object, re-emitting stored chains (§6.1's pinned seam). Verify the staged artifact by re-reading its own manifest (compose-side sanity: parseable, counts match the store).
  3. PUBLISH
    Promote staging → the generation's artifact key (create-if-absent, the chunk D promotion discipline); record it in the registry; respond 307. Subsequent generations orphan old artifacts for GC (§9).
  4. ENGINE SIDE
    The landed boot import ingests it: vetting, origin-dedup against local state, R16 keys, chain sources installed — all as merged with chunks A+B. Local overlap dedups by origin (an engine re-importing work it originated is the designed no-op).

Sizing honesty: the artifact is the merged scope, so it is as big as the retention policy allows the scope to be (§9 is the control surface); engines pay one download + one metadata import per boot, both budget-bounded with cold-start as the floor. Scope-slicing / per-workload artifacts are the natural future refinement and are shelved with the analysis seam — the merged view makes them possible, which is part of the point of having it.

9. Retention and pruning, service-side

The idea in three sentences. The merged view is pruned by the engine's own prune machinery — persisted edges are the retention roots (the union of what announcing engines retained), the existing policy vocabulary (KeepDuration, size targets, filters) configures per-scope limits, and the edge-cut + ownership-cascade model does the rest, exactly as it does on any engine. Blob retention follows metadata retention: the CAS's live set is the union of chain-blob digests referenced by live merged stores — a direct query over record-visible state, not a manifest union — and mark-sweep deletes the rest, safely at any aggressiveness because sparseness is legal (M5). Prune is the scope-size control surface, which makes it the artifact-size control surface (§8).

THE DECISIONS THIS SECTION MAKES
  1. Metadata prune = Cache.Prune over the merged store, per-scope policy from manager configuration (v1 defaults: a keep-duration plus a max-store-size target), run under the scope lease at ingest-time thresholds or on a period; a prune that cuts anything bumps the generation (the next artifact reflects it).
  2. Blob GC = mark-sweep over the CAS: live set enumerated from result_content_chains across live merged stores (+ a staging/pending safety window); orphaned checkpoint and artifact objects of superseded generations sweep on the same job. The chunk F GC-inventory notes fold in here.
  3. Prune-vs-announce interplay is the landed churn model: a pruned row re-announced by an engine that still has it re-enters (origin-dedup makes it exactly once); fleet-wide convergence comes from engines themselves pruning and the manager's policy horizon — the measured churn-not-growth argument carries over with the manager as the composition point, and the growth gate (M3) measures it there.

10. The upload-decision policy

The idea in three sentences. One server-side function owns "what do we want uploaded": requestedBlobs(view, casInventory, announcement) → requested, declined (with reasons) — the direct descendant of the v2-era server policy, now standing in front of a merged view instead of a per-source blob map. v1 policy: request every chain blob the announcement offers that the CAS does not have verified-present — maximal caching, minimal cleverness, always sparse-safe. The hook is the named convergence seam with the cache-performance analysis workstream: what-if-cached analysis produces per-record worth signals ("caching this saves X across the fleet; this is churn"), and when that lands, the policy consumes it here — same function, same protocol, smarter answer.

THE DECISIONS THIS SECTION MAKES
  1. The hook signature and home: manager-core, evaluated at announce time post-merge (§7.2), returning the requested set plus typed decline reasons (already_present, policy_declined, …) that land in events and counters (M6) — falsifiable from day one.
  2. v1 = all-missing-immutable-chain-blobs. Mutable-owner content never crosses (landed R4 semantics); everything else the fleet produced is worth having until analysis says otherwise.
  3. The analysis seam, named: the wcprof cache-performance workstream's what-if-cached output is the intended v2 policy input, per the owner's long-standing intent; additionally the merged view powers the should-be-cached vs is-cached insight (§11) that previews the same signals for humans first. Nothing in the protocol changes when policy smartens — only the answer.

11. Insight over the merged view

The idea in three sentences. The merged view is the insight substrate Erik asked for — "all of the cache from all of the engines is one big merged view" — and insight becomes direct queries over record-visible state: what the fleet caches, who produced it (origins), what content backs it (chains × CAS inventory), what gets reused vs sits cold, growth over time, prune pressure. The converged chunk F machinery re-homes with its hardest part deleted: there are no opaque bundles to best-effort-index anymore — the "indexer" collapses into scope-store queries the manager can run natively, while the event log, CAS statistics, dashboard rendering, and read-only discipline carry over as built.

THE DECISIONS THIS SECTION MAKES
  1. Surfaces (re-derived from chunk F): per-scope inventory (rows, classes, chains, CAS bytes, coverage = chain blobs verified-present / referenced), the event log (announce/decide/compose/prune/GC, typed + sanitized as converged), growth series by generation, and the dashboard (plain server-rendered HTML + SVG, as converged) — now including the first should-be-cached vs is-cached panel: offered-vs-requested-vs- declined tallies from §10's counters, the human preview of the analysis seam.
  2. Mechanism: read-only queries against scope stores (activated read-only from checkpoints — never against the live write path) + Postgres (registry, events, CAS inventory). The read-only discipline test carries over verbatim (S7's spirit lives here: insight has no write path into cache state).
  3. Chunk F disposition: event/CAS/dashboard/read-only machinery re-homes (~its own estimate: 70% neutral); the bundle-facts indexer and per-bundle coverage semantics retire with the architecture that needed them.

12. Version alignment

By owner ruling, the fleet and the manager are version-aligned and compatibility machinery is out of scope. Concretely: the manager is built importing the engine module at a pinned version; every engine-facing request carries the engine's version and persistence schema version; the manager asserts equality with its own and rejects mismatches with a typed, counted 409 — redeploys align the fleet, and that is the whole mechanism. A manager upgrade whose engine module changes the persistence schema wipes its merged stores (the sanctioned wipe-on-upgrade rule, now at fleet scale) and bumps generations; the view rebuilds from engines' ongoing announcements — which is the same honest path as M2's disaster recovery, exercised routinely enough to stay real. Checkpoints and artifacts are schema-tagged in the registry so a stale object can never be restored into a newer manager. What this design deliberately does not contain: version negotiation, dual-schema reading, migration code, or any decision shaped by redeploy avoidance.

13. The dev stack and the test ladder

The load-bearing placement decision (flagged for owner veto): the manager-core lives in dagger/dagger as a Go package (working name engine/cachemanager): scope-store lifecycle (§6), ingest+decide (§7), compose (§8), prune loop (§9), the policy hook (§10) — everything that is cache semantics. The dagger.io service is the shell: tenancy/auth, Postgres registry + events, real CAS backends, HTTP surface, deployment. Rationale: the core is nothing but engine code orchestrated (it imports dagql either way — from inside the same repo, the import is natural and version skew is impossible by construction); R11/M7 in-repo provability then covers the REAL merge/decide/compose semantics rather than a protocol-faithful fake; and the version-alignment story (M8) collapses to "the shell builds against the same commit." The prior test-service-vs-real-service drift problem disappears: the in-repo test harness runs the actual manager-core over filesystem storage. What stays proprietary is the shell — the product surface, tenancy, operations.

  1. UNIT (dagger/dagger)
    Manager-core: ingest idempotence (M3 red test), decide-policy matrix, compose round-trip (merged store → artifact → fresh engine store, keys as digest projections), checkpoint/ recovery (crash between flush and registry commit ⇒ previous generation), lease serialization, the nil-snapshotter compose red test (§6.1).
  2. IN-REPO INTEGRATION (dagger/dagger)
    The chunk C harness re-targeted: N dev engines + the manager-core behind a thin test HTTP shell (filesystem CAS, static token) as Dagger services. The proof set of §14 runs here — real merge, real negotiate, real artifacts, no cloud stack (M7). The conformance suite re-derives for the new protocol and runs against the test shell (rung 1) and later the real shell (rungs 3–4).
  3. SHELL HARNESS (dagger.io)
    Real handlers + Postgres + MinIO, no dev stack, no credentials — the converged dev-server pattern with the manager-core wired in; conformance green here proves the shell adds tenancy without changing semantics.
  4. E2E (dagger.io)
    Full stack inside Dagger: API server (manager enabled) + Postgres + MinIO + keeper + ≥2 dev engines; lifecycle (announce-after-green via the salvaged command lane, export-then-teardown keeper sequencing), the multi-engine warm proof, growth gate, manager-restart-survival (M2), upgrade-wipe-rebuild (M8).
  5. LIVE (credential-gated, last)
    Deploy; the cloud warm proof (§14) with the same evidence contract as ever.
