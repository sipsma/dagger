Remote Cache — The Cache Manager

v1 draft  ·  successor to the superseded store-and-select design  ·  2026-07-07

Status. Draft for adversarial review. This document supersedes ../service/design.html (retained as the review-log record of the rejected architecture and of the landed engine work). It is written against the owner's architecture guidance of 2026-07-07, which is binding throughout, and against the salvage maps produced at the pause: the engine map (take-3 worktree SALVAGE-MAP-ENGINE.md) and the chunk C/D/F STATE-OF-WORK.md files. The reset design (../reset/design.html) and lessons L1–L8 remain fully binding; engine chunks A+B are landed reality (integration tip 07e050e233, schema 19) and this design consumes them as built.

1. The goal

The cache service is a cache manager: the component that holds the cache semantics of the fleet. It maintains one merged view of the cache across all engines in a scope — every result, every equivalence, every content chain, from everyone — and it makes the intelligent decisions that only that view makes possible: what is worth uploading, what should be cached and whether it is, what to prune and when. Engines remain the executors and the local caches; the manager is where fleet-level cache intelligence lives, and "smart" is a fundamental product feature, not an optimization to defer.

The concrete v1 loop:

  • An engine finishing work tells the manager what it has (metadata + content manifests — no bytes). The manager merges that knowledge into the merged view and answers with exactly which records' content it wants uploaded; the engine uploads those blobs and nothing else. The upload decision lives server-side.
  • A booting engine downloads its scope's merged artifact — the composed, deduplicated state of everyone's cache — and imports it through the exact machinery it already uses (landed chunks A+B), as the single-artifact case of what it already does. Content still moves lazily, by digest, on demand.
  • The manager's view is durable (service restarts lose nothing), idempotent under ingest (origin identity — landed — makes re-announcement a no-op), and pruned server-side with the engine's own prune machinery.

The proof is unchanged in spirit from every prior take: a cold run on one engine seeds the manager; a warm run on a fresh engine hits, with counters that would have failed loudly if reuse hadn't happened — plus the new, manager-specific proofs: N engines' work visible as one merged view, ingest idempotence measured server-side, and the upload decision demonstrably server-made.

Deliberately deferred (the seams exist; the cleverness comes later): the analysis-driven upload policy (§10 names the wcprof convergence seam explicitly — v1 policy is simple); server-only re-layering of the imported engine code; backwards compatibility across engine/service versions (§12 — alignment is assumed, by ruling).

2. The load-bearing structural decision

The merged view is the product, and it is held by the engine's own cache code running server-side. The manager embeds the engine's cache implementation — the e-graph, the persistence store, the bundle ingest/compose machinery, the prune engine — imported as a Go module from the open-source repo, and maintains one durable, per-scope cache store that every engine's exports merge into. Nothing about cache semantics is reimplemented, approximated, or mirrored: the code that decides equivalence on an engine decides it in the manager, because it is the same code. What the manager adds is what only a fleet-level component can add — the merged view itself, the upload decision, retention policy over everyone's cache, and the insight surfaces.

Two named couplings stay dead, one from each prior failure:

  • Opaque bundles / store-and-select (the superseded design): a service that stores exporter bundles as sealed units and only chooses which to hand back can never make an intelligent decision about a record — not what to request for upload, not what to prune, not what is worth caching — because it cannot see records at all. Every future capability of this product runs through record-level visibility; opacity caps the product at "a bucket with a listing," and that ceiling is not acceptable. Any proposal that reintroduces a semantics-blind serving path for metadata is this coupling returning (content blobs are the deliberate exception: they are opaque bytes by nature, addressed by digest — §7).
  • The fragile merge (the v2-era failure shape): a server-side merge whose state is process memory (every restart loses the fleet's accumulated cache and forces a re-seed), and whose ingest mints fresh row identity per arrival (import → re-export cycles compound rows without bound). Both defects were properties of that implementation, not of server-side merging — and both are now structurally closed by machinery that has landed: the merged store is a durable persistence store with the engine's own restore/flush lifecycle (§6), and ingest deduplicates by origin identity, the mint-exactly-once row identity that chunk A built and that protects any importer, engine or manager alike (§7). The pivotal inversion of the salvage: origin identity was built to protect engines merging bundles; its greatest value lands server-side, protecting the merged view.

Why importing the engine code is the implementation and not a shortcut: the merge is the hard part of this product, and the engine already implements it — equivalence classes with congruence, origin-idempotent arrival, per-result vetting with honest blast radii, reference rewriting, portable encoding, restore-deterministic keys, pruning with retention roots. Every one of those was designed, adversarially reviewed, and landed in the open-source engine within this program. Rewriting them server-side would be the ridiculous option; the previous era's server merge already validated that the engine's cache embeds and runs server-side (the failure was its statelessness and identitylessness, both since solved — above). Version alignment between the imported module and the fleet is assumed by ruling (§12), which is exactly what makes this clean: the manager is another consumer of the same code at the same version, not a protocol peer across a compatibility chasm. Layering the engine code so server-only concerns separate more cleanly is future work by ruling, not v1.

3. Requirements and non-goals

Normative. M-numbers are this design's requirements. Carried requirements from the engine fundamentals (R1–R16, reset design) remain in force for the engine side; carried S-requirements from the superseded design are renumbered here where they survive, and their dispositions are recorded in §4 round 0. Notably: old S7 (engine-schema-agnostic service) is retired by owner ruling — see M8.

M1 — One merged view per scope, record-visible

The manager sees every record from every engine as one cache — never sealed units it can't look inside.

The manager maintains, per cache scope, one merged cache store containing every ingested result row, identity table, and content-chain reference from every engine in the scope, held in the engine's own cache representation via the imported engine module. Every manager decision (upload, prune, insight) operates on records in this view. No serving or decision path treats engine-produced metadata as opaque. Content blobs are the deliberate exception: bytes are opaque, addressed by digest, stored in the CAS.

M2 — The merged view is durable

A manager restart loses nothing. The fleet's accumulated cache is state, not cache-of-a-cache.

The merged view survives service restarts and redeploys without re-seeding from engines: it is persisted with the engine's own persistence machinery and checkpointed to durable storage (§6). Losing it is a disaster-recovery event with a defined, honest recovery (engines re-announce over time; the view rebuilds), never a routine consequence of operations. In-memory-only merged state is forbidden.

M3 — Origin-idempotent ingest (was S2, re-homed server-side)

Announcing the same work twice — or from two engines that both imported it — adds zero rows to the merged view, ever.

Ingest deduplicates by the landed origin identity (chunk A): a row whose origin pair is already in the merged view is never re-created; identity evidence unions; re-announce is a no-op. The red test runs server-side from day one: ingest the same announcement twice ⇒ zero merged-view growth. The growth gate (≥3 cycles across multiple engines, flat modulo new work — was S3) is measured on the merged view.

M4 — The upload decision is the manager's

Engines propose; the manager disposes. What content gets uploaded is decided against the merged view, server-side.

The export protocol is negotiate-then-upload: the engine announces metadata + content manifests; the manager answers with the exact set of blobs it wants; the engine uploads those. The decision function is a named, server-side policy hook over (the merged view, the CAS inventory, the announcement) — v1 policy is deliberately simple (§10), and the hook is the explicit convergence seam for the cache-performance analysis workstream (wcprof what-if-cached): the long-standing intent is that analysis output decides what is worth caching. Engines never self-decide uploads beyond what the manager requested.

M5 — Cache traffic never breaks builds (was S4) + sparse safety (was S5)

Everything about the manager is an accelerator; blob availability is never a correctness input.

Announce/upload failure never fails a green run; boot-import failure or timeout degrades to cold start under a budget; blob-fetch failure at serving time falls through the landed source walk to the demote floor. Metadata may reference content the CAS no longer has, and nothing breaks — which is what makes manager-side blob pruning safe at any aggressiveness. Every degradation is loudly counted.

M6 — Falsifiable observability (was S8), now including manager semantics

Every merge, decision, and serve is countable; the proofs consume the counters.

Engine counters carry over as landed. The manager adds its own: per-ingest {rows_offered, rows_new, rows_deduped_by_origin, blobs_requested, blobs_declined}, per-compose {rows, chains, generation}, prune outcomes, CAS sweep tallies — each consumed by a named gate case or insight surface. Proof-of-reuse remains by consequence (random-marker equality) plus counters.

M7 — Credential-free development to the last step (was S9)

The full manager loop runs and proves itself with no external credentials.

The manager core is buildable and testable in-repo (§13): the merge, negotiate, compose, and prune loops run against filesystem storage in dagger/dagger integration tests; the dagger.io shell adds tenancy, Postgres, real CAS backends, and deployment. The only credential-gated step remains the live cloud deployment.

M8 — Version alignment assumed; compatibility out of scope

Engines and the manager run aligned versions. Mismatch is rejected loudly, never bridged.

By owner ruling, backwards compatibility is explicitly out of scope for this design: the fleet and the manager are assumed version-aligned (same engine module version, same persistence schema, same wire shapes). The manager asserts alignment per request and rejects mismatches with a typed error; a manager upgrade that changes the persistence schema wipes its merged stores (the sanctioned wipe-on-upgrade rule) and the view rebuilds from re-announcements. No migration code, no version bridging, no schema-agnosticism — the superseded design's S7 is retired, and designs must not be shaped by redeploy avoidance.

M9 — Session-resource soundness crosses intact (was S10)

Handle-form only, in the merged view as everywhere; the salt partition is visible and narrower than once thought.

The merged view carries session-resource dependencies in handle form only (guaranteed by the persisted encoding). As-built refinement carried from the pause: only URI-form secret handles and SSH-fingerprint handles are salted (per-engine partition); setSecret handles are salt-independent and portable. The partition surfaces at identity level (a different-salt engine simply has no candidates), and the typed eligibility counter exists for the same-engine shapes it can observe.

Explicit non-goals (v1) NON-GOALS

  • Opaque metadata anywhere in the manager. The rejected coupling (§2). Content blobs in the CAS are the sole sanctioned opacity.
  • Analysis-driven upload/retention policy. The hook is v1 (§10); the analysis consumer is the named next phase.
  • Backwards/forwards version compatibility. M8. Future "annoying boilerplate," by ruling — not fear, sequencing.
  • Server-only re-layering of the engine cache code. Import it whole; factor later if real needs emerge.
  • Cross-scope/cross-org content sharing, finer tenancy, salt unification. Carried deferrals.
  • Mid-serving engine import (R14 stands), continuous engine↔manager sync. Engines import at boot and announce at export points; anything streamier is future.
