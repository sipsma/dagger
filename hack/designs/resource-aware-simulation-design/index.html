§1 What this is and what it answers

wcprof is the Dagger engine's wall-clock profiler. It records three kinds of events at the engine's blocking choke points — timed operation intervals (ops), blocked-on intervals (waits), and non-blocking correlations (links) — into a capture file. An offline analyzer (wcanalyze) rebuilds the causal graph from a capture and replays it under counterfactual hypotheses: "what if this class of work were 2× faster?", "what if these results had been cache hits?". The replay produces a simulated makespan — the run's wall-clock time, measured as the latest finish minus the earliest start over the run's root operations.

The replay today assumes an infinite machine: unlimited CPU, unlimited memory, any number of processes runnable at once. This is stated in the code (replay.go:11-13: "assuming unlimited resources (never CPU/disk bound)") and in the profiler's README (engine/wcprof/README.md:121-124). The assumption is harmless for hypotheses that only remove or shrink work on an otherwise-unchanged schedule. It becomes the dominant error source the moment a hypothesis increases concurrency — which is exactly what cache-elision counterfactuals do when they remove producers and let the surviving work pack together at the start of the run.

This design adds a capacity-aware replay mode: the same recorded graph, the same compiled per-op timelines, executed under a finite CPU capacity, with per-exec CPU demands taken from measurement. It answers, honestly:

  • (a) When a counterfactual parallelizes a run more, where does the added parallelism stop paying because the machine is full?
  • (b) Would more CPUs have made this run faster? — answered in layers: a measured verdict, a measured bound, and simulated relief; never a fabricated point prediction (§8).
  • (c) (Down-payment only) Would this run fit on a smaller machine, and at what cost? Full multi-machine planning is a named seam (§14).
Two prior rulings bound everything here. (1) Only user execs — container processes — have usable resource measurements; engine-internal operations are never attributed resource usage. (2) The simulator only ever executes a fixed, documented scheduling policy under a hypothesis. It never searches for a good schedule — schedule optimization for precedence-constrained tasks on finite machines is NP-hard (literature: Ullman 1975; Blazewicz et al. 1983), and simulating a fixed policy is an O(E log E) discrete-event computation. That line is what keeps this project out of NP-hard territory.

§2 The recorded graph, the replay, and the three infinite-resource points

Op. One recorded operation interval, with identity (kind, class, instance ident), timestamps StartNS/EndNS (nanoseconds relative to the recorder's epoch), a structural parent, children, and wait edges (wcanalyze/graph.go:18-86).
Exec op. An op of kind exec — one container run. It is created around the whole container lifecycle (engine/engineutil/executor.go:135-146, "exec.run") and has one child op per setup phase (exec.<phaseName>, kind exec_phase (executor.go:216-231)), the last of which — exec.runContainer — contains the actual container lifetime. Inside that phase the profiler records two further exec_phase ops — grandchildren of exec.run — splitting engine overhead from user runtime: exec.containerStart (create/start) and exec.processRun (the user process, WorkType user), recorded with the runContainer phase as their parent (executor_spec.go:1429-1434). A never-started exec records no processRun (executor_spec.go:1432-1434).
Open op. An op that had not ended when the capture was dumped; its EndNS is the dump time and it is flagged Open (graph.go:73-74, 391-412).
Hit-short op. In a what-if-cached simulation, a call of a cached digest: it finishes at its start plus the hypothesis pull cost; its recorded self-time, waits, and children are not replayed (replay.go:482-489).
Self segments. An op's interval minus its children's intervals and its own wait intervals: the time the op was plausibly doing its own work (graph.go:589-606).
Fixed-delay wait. A wait on a named resource (a lock), replayed as a recorded-duration delay running concurrently with the op's other work (replay.go:79-87, 603-610).
The replay. Each op's timeline is compiled once into a flat program of actions — self segments, child spawns, waits — sorted by recorded time (compileProgram, replay.go:138-280). A simulation executes these programs and derives every op's simulated start and finish.

What must structurally change. The current simulation is a lazy, memoized recursion — finish(i) recursively finishes dependencies on demand (replay.go:451-503). An op's schedule depends only on its own dependencies, which is what makes the replay order-independent (asserted by the SimStartConflicts counter (replay.go:349-355)) and each simulation a cheap array DP over the compiled program. Under finite capacity, an op's progress rate depends on everything else running at the same instant — a global coupling. The capacity mode therefore uses a global time-ordered event loop (§4) over the same compiled programs. The infinite mode keeps its recursion, byte-for-byte untouched, and remains the default.

§3 The machine and demand model — exact semantics

§3.1 The machine

One machine with CPU capacity C, in cores (fractional allowed), from the capture header (emit E-R2, §6.2). All the capacity facts can constrain the engine simultaneously (a container can have both a cpu.max quota and a restricted cpuset), so C is the minimum over every present constraint — never a precedence pick:

C_rec = min( cpu.max quota/period    [if present and not "max"],
             |cpuset.cpus.effective|  [if present],
             runtime.NumCPU()         [present whenever E-R2 is] )

The engine may itself be capacity-limited (a CI engine container with a CPU quota) — that is why the host's core count alone would be wrong. The report prints each component and which one bound (the provenance line), not just the resolved number. If E-R2 is absent entirely (old captures; non-Linux), capacity mode refuses (gate G1, §10). A CLI override (-capacity-cores) exists for sensitivity analysis and always prints as an override.

C_rec vs C′. C_rec is the recorded machine's resolved capacity (above); C′ is whatever capacity a given simulation runs at — C_rec by default, a grid multiple or an override otherwise. Data-consistency checks (gate G5) compare measured demand against C_rec only: simulating at a smaller C′ deliberately puts demand above capacity — that is the sensitivity analysis working as intended, not an inconsistency.
Memory is not part of the scheduling model. Measured per-exec memory peaks feed feasibility checks and reporting only (§8.4). Simulating memory-constrained timing (swap, reclaim, OOM) from peak counters would be guessing nonlinear dynamics the data does not carry — refused.

§3.2 Which ops carry demand

Only exec ops carry CPU demand, because only they have a measured cgroup (one cgroup per container exec (executor_spec.go:1220-1242)). Every other op — calls, lazies, session phases, exec setup phases outside the demand window — has zero modeled demand and unchanged recorded durations. This is the declared model boundary from the prior ruling, restated in every capacity-mode report: engine-internal CPU use exists, is not modeled, and biases the model optimistic about available capacity.

§3.3 The demand window

Each exec op carries, from emit E-R1 (§6.1):

  • W — the container's total CPU work in core-microseconds: the final cumulative usage_usec from the exec cgroup's cpu.stat. (Cumulative counter ⇒ the final read is exact for the whole exec regardless of sampling interval — even a 300 ms exec has an exact total.)
  • [ws, we) — the process-run window: ws is the container-started boundary the profiler already captures for the exec split (executor_spec.go:1276-1289); we is the process-exit boundary — the instant callWithIO returns (executor_spec.go:1411-1424), before any cleanup runs. These are exactly the boundaries the recorded exec.processRun phase carries (executor_spec.go:1430-1431) — deliberately redundant with a recorded fact: the loader cross-checks them (gate G4), and a never-started exec (no processRun) explicitly carries no window. Setup phases lie outside the window; the cgroup has no user processes before ws. The cgroup files are read later, in cleanup (§6.1) — safe because the counters are cumulative and the container's processes are dead by then.
In-window self time.  SW = Σ length( selfSegment ∩ [ws,we) ) over the self segments of the exec op and ALL exec_phase ops in its nesting subtree (transitive descendants). Two details are load-bearing. Descendants, not children: the user-process phase exec.processRun is a child of the exec.runContainer phase — a grandchild of exec.run (executor_spec.go:1429-1434); a children-only rule would exclude it, and since a parent's self segments exclude its children's intervals (graph.go:589-606), the runContainer phase's self time is ~zero exactly where the window lives — SW would degenerate on every normal exec. No double counting: self segments are disjoint from child intervals by construction, so summing across the exec_phase subtree counts every instant at most once; the traversal stops at non-exec_phase boundaries, which is what excludes nested-client subtrees (§3.5). The exact extent of the wait/child exclusion: it covers recorded waits and child intervals of the dilation-set ops themselves (that is what SelfSegments subtracts). It does NOT cover nested-client subtrees: nested session ops are reparented as children of the exec op (graph.go:489-502) — siblings of the phase chain — so their intervals overlap exec.processRun without being subtracted from its self segments. That is deliberate: the recorded data carries no container-side blocking edge for nested calls (SDK clients routinely issue them asynchronously and keep computing), so treating a nested op's span as "the container was blocked" would be inventing a blocking fact. Demand therefore continues through nested-client overlap; the placement smear for a host that really did block synchronously is part of the declared simplification below, same B2 remedy.

Demand rate.  d = W / SW (cores) — the measured average rate over the container's own working time.
Declared simplification — attribution within the window. W is an aggregate counter for the whole container; the data cannot say when within the window the CPU was burned. The model places all of W uniformly on the in-window self segments (D_e, §3.5) — equivalently, it assumes the container's CPU use during the gaps in D_e (recorded waits of dilation-set ops and uncovered child intervals) is negligible, and that its CPU use is uniform elsewhere — including through sibling nested-client overlap, where demand deliberately continues (the no-suspension rule): a host that in fact blocked synchronously on its nested call gets its demand smeared over that span. Total W is conserved in every case; only the placement can be wrong, and no denominator choice fixes placement from an aggregate counter — every choice assumes one — so guessing a distribution would be compensation. Stated here, restated in the report's method note (§11.4); error direction not derivable in general; the designed empirical remedy is the B2 time-series refinement (Appendix B), triggered by calibration evidence.
  • d = 0 (a container that used ~no CPU) is legal: such an exec never contends and never stretches.
  • SW = 0 with W > 0 is degenerate recorded data (work with no working time): counted, excluded, gate G4 fails. Never silently absorbed.
  • d is never capped. Against the recorded capacity, d > C_rec means the measured data and the machine facts disagree (e.g. a quota-derived C_rec while the cpuset allowed more cores — a provenance defect): gate G5's condition. Against a simulated C′ < C_rec, d > C′ is simply a deep deficit: the allocator caps a = C′ and the window stretches by d/C′ — the sensitivity analysis working as intended (V-R4, V-R18).

§3.4 The stretch rule (what dilation means)

Active set A. The exec ops currently advancing an in-window self segment (not blocked on a join, not in setup, not finished).
Water-filling (max-min fairness with caps). Find the unique water level L with Σi min(di, L) = C (or L = ∞ if Σdi ≤ C); exec i receives allocation ai = min(di, L).
Progress rate. ri = ai/di ≤ 1 recorded-seconds per simulated-second (di=0 ⇒ ri=1).
The stretch-only rule is the honesty keystone. Nothing ever runs faster than recorded: the measured demand is a lower bound on what the process would have used on a larger machine, so simulating extra speed would be inventing data. If the machine can satisfy every active demand, everything runs at recorded speed; under deficit, contended windows dilate. What higher capacity can honestly do is un-stretch work that a tighter counterfactual had stretched — the "would more CPUs help?" question gets its answer from measured evidence instead (§8).

Why max-min fair sharing and not something else. The real engine imposes no exec scheduling of its own — the oci-max-parallelism flag is parsed (cmd/engine/main.go:782-793) but consumed nowhere in the Dagger executor path (verified by exhaustive grep; the only other reference is the config struct, internal/buildkit/cmd/buildkitd/config/config.go:123-145) — so containers compete under the kernel's fair scheduler. Max-min fairness is the standard fluid abstraction of a fair scheduler (literature), it is deterministic, and it has no integer-slot artifacts. (The phase-1 assessment rejected discrete core slots: measured demands are fractional, and list schedules are non-monotone in processor count — Graham's scheduling anomalies (literature: Graham 1966/1969) — which would make capacity-sensitivity curves occasionally report that adding cores slowed the run down: indefensible output.)

§3.5 Exactly which recorded time dilates

The window transform M_e — over recorded instants, case by case. D_e = the union of (self segments of dilation-set ops) ∩ [ws,we), in recorded order — §3.3's demand intervals. Gaps = the window minus D_e: every in-window instant not covered by any dilation-set op's self segment (recorded waits of dilation-set ops; child intervals not contributing self time through the traversal). NOT gaps: an exec_phase child's interval (the traversal descends into it) and a sibling nested-client overlap (it cuts only the exec op's near-empty self time — processRun's self segments still cover those instants: the no-suspension rule, mechanically). p(t) = the D_e length in [ws,t].

Case 1 — t inside a fragment: M_e(t) = the sim time at which e's executed fragment-time reaches p(t). This is a progress milestone: a first-class projected event — when a fragment is (re)projected at a rate change, every registered milestone inside it is re-projected at the interpolated sim time, with the same generation-counter invalidation as completions (otherwise a milestone projected under an old rate fires at the wrong time under exactly the contention this mode models).
Case 2 — t inside a gap: M_e(t) = the gap's sim start image + (t − the gap's recorded start), clamped to the gap's sim end image (gaps resolve by their own join/fixed-delay semantics, so their sim durations can differ from recorded; each clamp is counted — defensive, G6 family). A window truncated before a registered anchor fires it at the window's end image and counts it — never silent.

The pendingAnchor state. A registered-but-unfired deferred spawn puts the child in state pendingAnchor — global state owned by e's window progress, NOT by the registering parent, which moves on un-blocked. The parent's implicit joins treat a pendingAnchor child as unfinished: the parent blocks at that join point until the spawn fires and the child finishes (the recorded ordering constraint, unchanged). No deadlock on faithful data: window progress is carried by the phase coroutines, which never wait on the exec op's later actions; an unfaithful cycle lands in quiescence detection (G6).
What M_e means for the C′=∞ equivalence (G8) — scoped honestly. The M_e anchor is a deliberate refinement over the infinite mode, at every C′ including ∞: the infinite mode anchors a nested child at the exec op's local clock, and the exec op's own self time is nearly empty, so when a hypothesis factor scales the host exec's class, the infinite mode does NOT move the nested spawn at all — an existing modeling gap this design exposed (named as a §14 seam; fixing the infinite mode is out of scope). The equivalence contract: (1) graphs with no capacity data or no demand-carrying execs — every existing replay test graph — bit-for-bit, always; (2) demand-carrying baseline (factors 1) at C′=∞ — M_e is the identity — bit-for-bit; (3) demand-carrying under hypothesis factors at C′=∞ — bit-for-bit for every op EXCEPT M_e-remapped anchors and their causal downstream, with the remapped anchors asserted against hand-derived M_e-at-∞ values (V-R12/V-R21/V-R22 — the catalog asserts the divergence itself: it is the documented refinement, not an accident).

§3.6 What deliberately does not change

  • The infinite-resource mode: default, byte-for-byte untouched.
  • Compiled programs (replay.go:138-280): shared by both modes.
  • Fixed-delay lock waits: recorded durations in both modes.
  • What-if-cached hypothesis resolution (the elide-or-keep pre-pass): identical; capacity mode swaps only the replay executor underneath it (§13).
  • The what-if class ranking table (up to 200 classes × factors (replay.go:797-891)): stays infinite-mode in v1, labeled (§9; rationale §12).

§4 The capacity-aware event loop — exact algorithm

§4.1 State

Per op (dense arrays, same indexing as the compiled program): pc — next action index; localClock — the op's simulated clock; status ∈ {notStarted, runnable, inSelf(remaining recorded ns, dilated?), blockedOnJoin(target), blockedOnPend(child), finished}. Exec ops additionally carry window [ws,we), work W, in-window self time SW, demand d (precomputed at load), and a running ledger of allocated core-time (for conservation gate G7).

Global: an event queue — a binary heap of (simTime, rank, opID, generation). rank breaks ties in the same relative order the compiled programs use at equal recorded times (replay.go:188-211): gate events before spawns before segment completions before bookkeeping — so equal-time semantics match the infinite mode. opID breaks remaining ties; generation invalidates superseded entries (the standard discrete-event re-projection device: stale entries are popped and discarded). Plus: the active set A with current allocations, and a reverse-wait index (op → blocked waiters), built lazily from the compiled joins.

§4.2 Execution

Initialization: every root op is scheduled at its recorded start — an exact fact, exactly as the current replay pre-anchors roots (replay.go:408-419). An op's coroutine, when it runs at sim time t, executes its compiled actions in order, mirroring the infinite replay's action semantics (replay.go:560-617) with these operational differences:

actioncapacity-mode behavior
actSelf (rigid: non-exec, or outside the window) schedule completion at localClock + dur × factor (hypothesis factors compose exactly as today)
actSelf (dilated portion) enter the active set with the remaining recorded time; trigger a rate event (§4.3). Completion is projected at localClock + remaining/r and re-projected on every rate change. A segment straddling the window boundary is split at the boundary (V-R15) — in a capacity-mode-only precompute overlay (derived arrays keyed by action index), never in the shared compiled program: the infinite mode keeps executing the untouched program byte-for-byte, which is what makes gate G8/V-R1 hold by construction rather than by re-verification. Fragment rounding rule (nanosecond-exact C′=∞ equivalence): the current replay rounds once per action — int64(float64(dur) × factor) (replay.go:565); per-fragment rounding could drift ±1ns. The overlay computes fragment lengths as differences of cumulative rounded positions (round(prefixi+1·f) − round(prefixi·f)), which telescope to exactly the once-rounded total (V-R15, including the 3ns/f=0.9 adversarial case).
hypothesis factors on dilated segments (exact rule) a class factor f applied to a demand-carrying exec scales each dilated self segment's recorded time by f AND scales the exec's conservation target to W′ = d·T′ (T′ = the sum of once-rounded factor-scaled dilated fragment lengths — ≈ f·W up to the once-per-action rounding), leaving the demand rate d unchanged. Interpretation: "this class is f× faster" means the same job takes f× the time at the same CPU intensity — seconds and core-seconds shrink together. W stays untouched as the measured provenance value; every simulated ledger, the G7 check, and the stretched-exec accounting use W′ (= W with no factor). Consequences, asserted by V-R16: G7 checks delivered core-time against W′; d (the allocator's input) is factor-invariant; at C′=∞ the dilated segment's length is exactly the once-rounded dur × f, matching the infinite mode (G8). Scaling time but not work would make a "faster" hypothesis change the exec's CPU intensity — a physical claim the hypothesis does not make.
actSpawn set the child's start to the current localClock and schedule its first event — the same anchor rule as replay.go:580, executed forward in time. No out-of-order prefix machinery exists in this mode (the recursion's spawnTo (replay.go:627-678) is a lazy-evaluation device; a forward loop reaches children when their parents do). On faithful data both strategies anchor every child identically — asserted by V-R1.
actWaitJoin target finished ⇒ localClock = max(localClock, target finish); else block; wake on the target's finish at that time.
implicit joins (the pend list (replay.go:520-558)) unchanged ordering semantics — before an action at recorded time at, join every child whose recorded end ≤ at — but "join" means "block until that child's simulated finish" instead of recursive evaluation.
actWaitFixedStart/End (locks) the same max-gate arithmetic as replay.go:603-610, on the local clock.
what-if-cached states elided ops never scheduled (spawns skipped or waived per the resolution); hit-short ops finish at start + pullCost — the identical skip/waive logic the recursion applies (replay.go:456-489, 567-599), executed by this loop.

An op finishes when its program is exhausted plus the final implicit-join sweep (mirror of replay.go:616); its waiters wake.

§4.3 Rate events

Rates change only when the active set changes: a dilated segment starts (op enters A), completes, or its op blocks on a join (op leaves A). At each such event: recompute water-filling over A (O(|A| log |A|)); for each op whose allocation changed, carry its remaining recorded time over and re-project its completion event (bump generation, push a new entry). Between rate events, rates are constant — the simulation is exact, not time-stepped: no numerical integration, no dt, closed-form piecewise-linear progress.

§4.4 Termination, faithfulness signals, determinism

  • Quiescence with unfinished ops = the recorded causal structure could not schedule itself forward: a recorded cycle of waits, an inverted reference, a child its parent never spawns — exactly the unfaithful-data classes the current replay counts (CycleWarnings, UnschedulableOps (replay.go:326-343)). The event loop detects them structurally: nothing runnable, ops unfinished. Handling: count per break (gate G6 fails), break deterministically — anchor the lowest-op-ID blocked op at its recorded offset from its nearest started ancestor (the same damage-bounding anchor the recursion uses (replay.go:694-704)) — and continue. Never silent, never absorbed.
  • Determinism by construction: the event order (time, rank, opID) is total; water-filling is deterministic; no map iteration order reaches results. V-R11 asserts bit-identical outputs across input permutations. The recursion's SimStartConflicts order-independence signal has no analog here (a forward loop computes each start exactly once); a defensive never-two-starts counter replaces it, expected 0 always.
  • Machine-seconds conservation (gate G7): the loop asserts, at each exec's window completion, that delivered core-time equals the simulated work target W′ = d·T′ (T′ = the sum of once-rounded factor-scaled dilated fragment lengths — §4.2's rounding rule; = the recorded dilated time with no factor). Deriving W′ from the same rounded T′ the time arithmetic uses makes the identity exact: window time advances at a/d while a is delivered, so delivered ≡ d × window-time-advanced ≡ d·T′. Bookkeeping exactness, not a tolerance; raw measured W is provenance only.

§6 The emits — field-by-field, justified or refused

Doctrine. Every emitted field must have a consumer in the analysis that decides something with it; fields without a deciding consumer are refused (listed, with reasons, revisited when a consumer exists). All emits are additive: zero behavior change when wcprof is off; no existing field changes meaning.

§6.1 E-R1 — per-exec final resource totals

Mechanism. One read of the exec cgroup's files at container exit — independent of the OTel metrics sampler and its gates. The existing sampler only runs when the exec has a call digest and builds an OTel meter (executor_spec.go:1221-1242); the wcprof emit must not inherit that gate: execs without call digests exist (execIdent falls back to the raw exec id (executor.go:130-133)), and a capacity model missing any exec's demand refuses (gate G3), so the emit must cover every container.

Two boundaries, deliberately different. Timestamps at the process-exit boundary: WindowStartNS is the started-callback instant (executor_spec.go:1276-1289); WindowEndNS is captured where callWithIO returns (executor_spec.go:1411-1424) — the same instants the recorded exec.processRun phase uses (executor_spec.go:1430-1431). NOT at cleanup time: cleanup latency is engine overhead, not container runtime, and must not widen the window. File reads in cleanup: the cgroup files are read in runContainer's cleanup path, immediately before the sampler-cancel cleanup, with the same path resolution the sampler uses — the OCI spec's cgroup path (state.spec.Linux.CgroupsPath (executor_spec.go:1220)) joined under the cgroupfs mountpoint /sys/fs/cgroup exactly as resources.NewSampler does (sampler.go:14, 40); the raw spec path alone is relative and would be the wrong path. Reading after process exit is safe: the counters are cumulative and the container's processes are dead (the post-we tail is teardown-only, declared in §11.4); the cgroup provably still exists there — cleanups run LIFO (util/cleanups/cleanup.go:49-55) and the runc delete cleanup is registered earlier (executor_spec.go:1216 vs 1247), so it runs later. The outer RunContainer attaches the snapshot to the profiler op before ending it (execOp ends at executor.go:175, after c.run's deferred cleanups at executor.go:203 — verified ordering). New recording API: Op.SetResources(snap) in engine/wcprof/record.go, fixed-size numeric fields on the op's event; no string interning involved.

§7 Loader, graph, and per-source capability changes

  • Op gains Resources *OpResources — nil means "not recorded" (old captures, OTel source, non-exec ops); carries the E-R1 fields plus per-family presence booleans. Never zero-filled.
  • Graph gains Machine *MachineFacts (nil = not recorded): E-R2 fields, presence flags — ALL the observed constraint components (consumers see every input), the resolved capacity C_rec (the §3.1 minimum), and a provenance enum naming which constraint was binding (quota | cpuset | numcpu | absent). The enum means only "which one bound"; the non-binding inputs are not discarded.
  • Demand derivation (d, SW, window∩self-segment splits) happens once at load into dense per-op arrays alongside program compilation; degenerate cases counted for G4.
  • The per-source capability table (the analyzer's existing honesty surface for native-vs-OTel differences) gains a "resource data" row: native = yes, with kernel-dependent families flagged per capture; OTel = no (v1).
  • LoadMulti (multi-dump merges of one recorder run (graph.go:249-284)): machine facts must agree across dumps of one epoch; a mismatch is a load error (same epoch = same engine process; disagreement means the facts changed mid-run — surfaced, not averaged).

§8 The measured-evidence layer and the "more CPUs?" verdict

Everything in this section is computed from measured data (E-R1/E-R2), independent of any simulation — so the strongest available answer is always given from measurement alone, with simulation reserved for counterfactual packing.

§8.1 Saturation timeline

S(t) := Σ of di over execs with an in-window self segment containing t — the same demand intervals the simulator charges (§3.3/§3.5: demand is inactive during the gaps in D_e — dilation-set waits and uncovered child intervals — and outside the window; sibling nested-client overlap does NOT suspend demand). Summing over whole windows instead would fabricate saturation during known blocking — exactly the intervals the model excludes. S(t) is piecewise-constant with breakpoints at in-window self-segment edges, computable exactly by an event sweep. SAT := maxt S(t)/C_rec. Also reported: total duration where S(t) > 0.9·C_rec ("saturation windows") and where S(t) > C_rec (a measurement/capacity inconsistency — gate G5's timeline condition).

§8.2 CPU contention ledger

PSI (pressure stall information) is a Linux kernel facility measuring time tasks were runnable but stalled waiting for a resource. Per cgroup, cpu.pressure accumulates: some = time at least one task was stalled on CPU; full = time all non-idle tasks were stalled simultaneously (pure loss). These are direct kernel measurements of CPU starvation, per exec. STALL% := Σ PSICPUSomeUS / Σ window durations.

The ledger prints per-exec and per-class stall totals, absolute and as window fractions, with full split out.

§8.4 Memory feasibility — annotation, never timing

For any capacity-mode schedule: sweep Σ MemPeakBytes over sim-concurrent exec windows; where the sum exceeds MemTotalBytes, annotate: "this schedule co-locates exec peaks summing to X on a machine with Y — infeasible as scheduled; timing impact NOT modeled." Peaks need not coincide in time within windows, so the sum is a conservative over-estimate — stated in the annotation text. It never alters timing.

§11.4 Noise: stated, bounded, never compensated

Known noise sources, each stated in the report's method note: 5 s sampling does not affect final totals (cumulative counters, final read at end of life — §6.1); window timestamps are callback-time, not cgroup-file time (sub-ms skew); PSI totals carry kernel bookkeeping granularity; whole-window averaging smears bursts (Appendix B is the designed refinement, deferred until CAL data shows it is the dominant error); the in-window placement of the aggregate W is the §3.3 declared simplification (the container is assumed CPU-idle during the gaps in D_e and uniformly busy elsewhere, including through sibling nested-client overlap — total W conserved, placement not derivable from an aggregate counter); the post-we teardown tail is included in W but not in the window (negligible, teardown-only). None is corrected for; they are why G2/G5 carry measured-floor tolerances instead of zero.

§11.5 Real-engine calibration (evidence committed under hack/logs/)

Method mirrors the established what-if-cached calibration harness (same workloads, same dump discipline) — with the advantage that capacity is directly manipulable, which cache state never fully was:

  • CAL-1 — baseline residual floor. N unconstrained captures across the workload set; distribution of G2 residuals; sets and validates the G2/G5 tolerance constants (documented in the calibration doc; constants updated by evidence only).
  • CAL-2 — constrained prediction, both directions. Capture unconstrained; predict makespan at C=k via the grid; rerun the same workload on the same engine under cgroup cpu.max=k; compare — per-class stretch and makespan, decomposed gap sources per the calibration-doc precedent (context lines, no single grade). Then the reverse: capture constrained, predict at C′=host, compare with the unconstrained run. Honest expectation, stated before running: stretch-only semantics predicts (approximately) no relief in this direction — the constrained capture's demands were measured under throttling, so they fit its C_rec, and raising capacity un-stretches nothing. The comparison against the real unconstrained run therefore quantifies the under-prediction gap — the observed-demand-lower-bound limit made empirical — and the calibration reports that gap as the characterized limit, never as model failure and never as something to tune away. Companion characterization (not an assertion): compare the constrained run's PSI stall totals against the actually-measured speedup, to characterize how the §8.3 measured-ceiling layer relates to realized relief on this workload set.
  • CAL-3 — evidence-layer sanity. On CAL-2's constrained run, PSI stall totals must be large and the verdict must say yes-evidence; on the unconstrained run, near-zero and "no". A failure here is a data-pipeline defect (fix the emit), never a model tuning knob.

§12 Performance and complexity

  • Events: one per compiled action plus one per dilated-segment boundary — O(total actions), the same asymptotic count the recursion touches; heap cost O(log queue).
  • Rate events: only exec window entry/exit/block/wake. Water-filling is O(|A| log |A|) per rate event; re-projection touches only active dilated execs. |A| is the number of concurrently running containers — dozens, not thousands, on real captures.
  • Expected cost vs the current DP: constant-factor worse (heap + ledger bookkeeping). Hypothesis, to be measured in implementation and recorded: ≤ 5× the flat replay on multi-million-op captures — comfortably fine where capacity mode runs (baseline + explicit hypotheses + grid ≈ tens of sims), and the stated reason the 200-class ranking grid stays infinite-mode in v1 (revisit trigger in §9).
  • Memory: O(n) dense arrays alongside the existing program (statuses, ledgers, queue).

§13 Composition with what-if-cached

The what-if-cached machinery is unchanged through resolution: hypothesis → static elide-or-keep pre-pass → per-op elision/hit state. Capacity mode plugs in at the executor level only:

  • Elided ops: never scheduled; spawns skipped or waived exactly per the resolution — the same flags the recursion consults (replay.go:456-489, 567-599). An elided exec never enters the active set and never contends (asserted, V-R10).
  • Hit-short ops: finish at start + pullCost; no demand.
  • The ElidedOpDemanded faithfulness counter carries over unchanged: a demand on an elided op in the forward loop is the same pre-pass contradiction — counted, gate-failing.
  • Relation gate (V-R10, also printed at runtime): per schedule, for the same hypothesis, capacity-mode makespan ≥ infinite-mode makespan (and likewise for the baseline) — capacity can only delay a given schedule. The gate is deliberately NOT the savings-difference inequality (savings_cap ≤ savings_inf): that is false in general — when the capacity baseline carries stretch, a hypothesis that relieves contention can save more under capacity than under infinity. The per-hypothesis report prints both savings side by side; the honest headline is the capacity-mode number.

§14 Seams named, not built

  • Ranking under capacity — once the measured event-loop cost allows a 200-sim grid (trigger recorded at §9).
  • OTel parity (§6.3) — metrics-stream ingestion + span join in the OTel loader.
  • Remote-cache upload intelligence — the planned cache service consumes what-if savings as its value-of-caching input; capacity-aware savings make that honest on busy machines. Interface unchanged: hypothesis in, honest saving out.
  • Multi-machine planning (question c) — the event loop generalizes to multiple capacity pools plus a simulated assignment policy (never an optimizer). Blocked on data that does not exist yet: cross-machine transfer costs, multi-engine traces. The v1 down-payment is the downward half of the sensitivity grid (machine right-sizing).
  • Aggregate engine-usage lane — Appendix A: designed, deactivated pending ratification.
  • Infinite-mode nested-anchor gap (found during this design, §3.5): the infinite replay does not move a nested-client spawn when a hypothesis factor scales its host exec (the exec op's own self time is nearly empty, so the parent clock never traverses the scaled work). The capacity mode's M_e anchor is the refinement; back-porting it to the infinite mode would change existing behavior and is deliberately out of scope here.

Appendix A — aggregate engine-usage lane (designed, deactivated)

If ratified: E-R2 gains one additional emit — the engine cgroup's own cumulative cpu.stat usage_usec at dump time (one aggregate number; under LoadMulti, per-dump samples give a coarse background series). Consumer: capacity honesty — Ceffective(t) = C − (engine aggregate rate − Σ exec rates), clamped ≥ 0, replacing the constant C in the water-filling (§3.4) and the saturation timeline (§8.1). No attribution to any internal operation ever occurs: the lane is one anonymous background band. Well-definedness requires the engine cgroup to contain the exec cgroups so the subtraction means something. That containment is a precondition to verify at implementation time, not a code-proven fact: the available citations (the OCI spec's cgroup path (executor_spec.go:1220); the sampler's mountpoint join (sampler.go:14, 40)) establish only where paths are read from, not the parent/child relationship. Containment is expected from runc/OCI cgroup defaults, and the emit would gate on verifying it (comparing the engine's own cgroup path against each exec's) — refusing the lane, presence-flagged, where it does not hold. Deactivated until ratified because it is adjacent to the attribution ruling.

Appendix B — time-series demand refinement (B2, deferred)

The water-filling uses the current interval's demand; rate events gain sample-boundary crossings. Everything else — allocator, gates, catalog — is unchanged in shape; V-R3/V-R5 gain piecewise variants. Volume: ~12 samples/minute/exec, packed array field. Deferred: no consumer until calibration evidence demands it.
